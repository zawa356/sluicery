# 2. 403 の根本対処

## 2.1 有力な仮説

yt-dlp の YouTube 抽出は **JS ランタイムを要求する**ようになっている。既定で有効なのは deno のみで、JS ランタイム無しでの抽出は非推奨とされ、一部フォーマットが欠落する。

JS ランタイムが無いと `n challenge solving failed` が発生し、その状態で 403 が出るケースが報告されている。

**sluicery のコンテナには JS ランタイムが入っていない。** これが Phase 8 の 403 多発の原因である可能性が高い。

裏付け：基本設計の記録によれば、**Blender 公式チャンネルの YouTube 版素材でも 403 が出ている**。アクセス頻度の問題ではなく環境側の問題を示唆する。

## 2.2 調査手順

1. Phase 8 の実行ログを確認し、**`n challenge solving failed` の警告が出ているか**を調べる
2. 出ていれば仮説が裏付けられる。出ていなければ別要因なので §2.5 へ
3. 現在の 403 の分類を確認する（おそらく `failed`）

## 2.3 Deno の導入

**イメージに同梱する。** D-002（ffmpeg）と同じ方針とする。

- バージョンを固定し、**checksum を検証する**
- `ARG DENO_URL` / `ARG DENO_SHA256` の build-arg 化（D-002 の復旧手順と同じ考え方）
- Dockerfile のコメントに、上流のローテーション時の復旧手順を書く
- **イメージサイズの増分を計測し、README の実測値を更新する**

導入後、yt-dlp が Deno を検出することを確認する。検出されない場合は `--js-runtimes` の明示指定が必要かを調べ、必要なら**オプション合成の L1（予約引数）に加える**。

## 2.4 403 の再分類（重要）

**403 を `failed` から `blocked` に変更する。**

理由：403 は「一時的な失敗」ではなく「弾かれている」状態である。PO トークン無しのリクエストは 403 を返すか、アカウントや IP がブロックされうるとされており、**即座にリトライすると状況を悪化させる。**

`blocked` にすることで、

- attempts を消費しない
- `blocked_until` で間隔を空けられる

**403 用の再試行間隔は通常の `blocked` より長く設定すること。**

| 設定キー | 既定 |
|---|---|
| `worker.blocked_retry_403_sec` | 3600 |

同様に「Sign in to confirm you're not a bot」も `blocked` に分類する。403 とはメタデータ要求とメディア要求という違いはあるが、根本原因は共通である。

## 2.5 検証（少量のみ）

**大量アクセスをしないこと。** 状況を悪化させる。

| # | 手順 | 期待結果 |
|---|---|---|
| 1 | Deno 導入後に `ytdlp probe` を1件 | `n challenge solving failed` が出ない |
| 2 | D-022 の YouTube 版素材を1件 fetch | 403 にならず取得できる |
| 3 | Phase 8 で `failed` / `blocked` になった Target を**3〜5件だけ**再試行 | 成功率が改善する |
| 4 | 403 を意図的に発生させる（不可能なら省略） | `blocked` に分類され attempts が増えない |

**#3 で 5件を超えて試さないこと。** 改善が確認できればそれで十分。

## 2.6 解消しなかった場合

**止まらない。** 以下の順で進める。

1. 結果を記録し、未解決事項として残す
2. **Part A を継続する**（Cookie サポートを実装する）
3. **Part A 完了後、Cookie を使って §2.5 の #2・#3 を再検証する**
4. それでも解消しない場合、記録して Part B 以降を継続する

Cookie で解消する可能性があるため、Phase 9 の実装後に再評価の機会を設ける設計とする。

なお、PO トークンを渡してもボット判定を回避できないケースが大半になっているという報告があるため、**PO Token プロバイダの導入は本フェーズでは行わない。** 必要になれば別途検討する。

# 4. 認証

## 4.1 ユーザー作成

- 初回起動時、`.env` の `ADMIN_USERNAME` / `ADMIN_PASSWORD` でユーザーを作成する
- `ADMIN_PASSWORD` が空ならランダム生成し、**起動ログに一度だけ出力する**
- **必ず `UserRepository.create_single()` を経由する**（生の `session.add(User(...))` では2件目を防げない）
- パスワードは **argon2** でハッシュ化する

README と `docs/deployment.md` の「Phase 9 で実装予定」という記述を、実装済みに更新すること。

## 4.2 セッション

- Cookie ベース。**`HttpOnly`、`SameSite=Lax`**
- `Secure` は設定で切り替え可能にする（リバースプロキシ経由の HTTPS を想定）
- 署名に `itsdangerous` を使う。**鍵は `SECRET_KEY` から導出する**（`SECRET_KEY` そのものを使わず、用途別に派生させる）
- 有効期限を設ける（`auth.session_max_age_sec`、既定 30日）
- **ログイン成功時にセッション ID を再生成する**（セッション固定攻撃対策）

## 4.3 レート制限

- 既定：5回失敗で15分ロック（要件定義 §12）
- 設定可能にする（`auth.max_login_attempts` / `auth.lockout_sec`）
- **ロック状態を DB に持つ。** プロセス再起動で解除されると意味がない
- ロック中は正しいパスワードでも拒否する
- **エラーメッセージでユーザー名の存在有無を漏らさない**（「ユーザー名またはパスワードが違います」で統一）

## 4.4 CSRF 対策（必須）

**フォーム送信と HTMX による状態変更リクエストに CSRF トークンを要求する。**

- トークンをセッションに紐づけて発行し、テンプレートに埋め込む
- HTMX のリクエストには `hx-headers` または hidden input で付与する
- **GET 以外の全てのエンドポイントで検証する**
- 検証失敗は 403 で拒否する

`SameSite=Lax` だけでは不十分（トップレベルナビゲーションによる POST は防げないケースがある）。

## 4.5 パスワード変更

- UI から変更できる
- **現在のパスワードの入力を要求する**
- 変更後、既存セッションを無効化する（自分自身を除く、または全て無効化して再ログインを求める）

## 4.6 認証の適用範囲

| パス | 認証 |
|---|---|
| `/healthz` | 不要 |
| `/login`、静的ファイル | 不要 |
| **それ以外の全て** | 必要 |

**ホワイトリスト方式にすること。** 「認証が必要なパスを列挙する」方式は、新しいエンドポイントを追加した際に守り忘れる。

# 6. Cookie サポート（要件定義 §9.7）

## 6.1 スコープ

yt-dlp に Cookie を渡す機能。**既定で無効**であり、Playlist 単位のオプトインとする。

## 6.2 保存

- Cookie ファイルの内容を **`EncryptedJSON`（Fernet）で DB に保存する**
- 保存先は Playlist に紐づく（Storage のクレデンシャルと同じ扱い）
- UI では write-only。設定後は「設定済み」表示のみ
- 設定エクスポート（Phase 17）の対象外

## 6.3 実行時の展開

- **tmpfs（`/run/sluicery`）に展開する。** 平文をディスクに残さない（要件定義 §6.5）
- パーミッションは 600
- **実行後、確実に削除する。** 例外発生時も削除されること（`try/finally`）
- ファイル名は推測できないもの（UUID）にする

## 6.4 yt-dlp による書き戻しの扱い（重要）

**yt-dlp は `--cookies` で渡したファイルを更新することがある。**

方針を決めて実装すること。**推奨は「書き戻しを DB に反映しない」（読み取り専用として扱う）。**

理由：書き戻しを反映すると、並行実行時に競合する。また Cookie の更新は本質的にセッション維持のためであり、失効したら再入力を求める方が単純で安全。

**この判断を記録すること。** 将来 Cookie が頻繁に失効して運用が回らない場合、再検討の材料になる。

## 6.5 UI での注意喚起

要件定義 §9.7 の通り、**アカウントに紐づく大量アクセスは停止リスクがある**旨を UI に表示する。

有効化時に確認を求めること。

## 6.6 ログとマスク

- **Cookie ファイルのパス・内容を一切ログに出さない**
- コマンドラインプレビュー（Phase 4）で `--cookies` の引数をマスクする（既存のマスク層に追加）
- エラーメッセージに Cookie の内容が混ざらないこと

## 6.7 `--cookies-from-browser` は使わない

コンテナ内にブラウザが無いため機能しない。**予約引数として拒否するか、明確なエラーメッセージを出すこと。**

# 7. レビュー①（セキュリティ重点）

記録は `docs/reviews/phase9.md`。

**特に見てほしい観点**をレビュー役への指示に含める。

- **CSRF がすべての状態変更エンドポイントで検証されているか**
- 認証がホワイトリスト方式で、抜け道がないか
- **セッション ID がログイン時に再生成されているか**
- レート制限が DB に永続化され、再起動で解除されないか
- エラーメッセージからユーザー名の存在が漏れないか
- **Cookie ファイルが例外発生時も確実に削除されるか**
- Cookie の内容・パスがログ・UI・コマンドラインプレビューに現れないか
- `SECRET_KEY` が用途別に派生されているか（セッション署名と暗号化で同じ鍵を直接使っていないか）
- パスワードが argon2 でハッシュ化され、平文がどこにも残らないか

**重大指摘が出た場合、§0.2 の3に該当するかを判断する。** 対応方針が一意なら対応して Part B へ進む。

# 13. ログ閲覧とキャンセル

## 13.1 ログ閲覧

- Run 単位のログをブラウザで表示する
- **必ずマスク層を通す**（yt-dlp / rclone の stderr にクレデンシャルや Cookie パスが含まれうる）

**パストラバーサル対策を必ず行うこと。**

- ログのパスをユーザー入力から組み立てない
- **`run.log_path` を DB から取得し、`DATA_DIR` 配下であることを検証する**
- 任意のファイルを読める経路を作らない

大きなログは末尾N行のみ表示し、全文はダウンロードできるようにする（ダウンロードもマスク層を通す）。

# Part D — スケジューラ

# 15. 基本方針

## 15.1 実行主体

**`app` サービスのみがスケジューラを動かす。** worker は動かさない。

複数プロセスでスケジューラを動かすと、同じジョブが多重実行される。

## 15.2 ジョブストア

APScheduler の SQLAlchemyJobStore を使い、**既存の SQLite に格納する**（要件定義 §10.1）。

**ロック競合に注意すること。** WAL モードだが、ジョブストアの更新とアプリの書き込みが競合しうる。競合が観測されたら、別ファイルへの分離を検討し、判断を記録する。

## 15.3 ホストの cron を使わない

要件定義 §4.3 の「残骸を残さない」原則。**ホストの crontab / systemd timer を一切使わない。**

---

# 16. スケジュール機能

## 16.1 分離スケジュール

**discover と download に独立した cron を持たせる**（要件定義 §10.2）。

| 対象 | グローバル既定 |
|---|---|
| discover | 6時間ごと |
| download | 6時間ごと |
| integrity check | 日次（**Phase 13 まで未実装。ジョブを登録しない**） |
| yt-dlp update | 週次（**Phase 15 まで未実装。ジョブを登録しない**） |

Playlist 単位で `discover_cron` / `download_cron` による上書きが可能。

## 16.2 タイムゾーン

**cron 式は `.env` の `TZ` で解釈する**（要件定義 §10.1）。DB のタイムスタンプは UTC のまま（既存の前提）。

**ここを混同すると、スケジューラと履歴表示が食い違う。** 変換箇所を一箇所に集約すること。

## 16.3 実行可能時間帯

`schedule.download_window`（既定 None）で、download を実行できる時間帯を制限する。

- 形式は `HH:MM-HH:MM`
- **日をまたぐ指定（`23:00-05:00`）を扱えること**
- 時間外は Task を投入しない
- discover には適用しない（メタデータ取得のみで負荷が軽いため）

## 16.4 ジッター

`schedule.jitter_minutes`（既定5）で、±N分のランダム遅延を入れる。複数 Playlist の同時刻集中を避ける。

## 16.5 一時停止

`playlist.paused` が true ならスケジュール対象から外す。UI から切り替えられる。

## 16.6 次回実行予定

**UI に次回実行予定時刻を表示する**（要件定義 §10.3）。`TZ` で表示すること。

## 16.7 misfire

停止中に予定時刻を過ぎたジョブについて、`misfire_grace_time` を設定する。

**既定：直近1回のみ実行する。** 無制限に積み上がらないこと（要件定義 §10.4）。

## 16.8 起動時の整合

- 前回異常終了で `running` のまま残った Task / Run を検出する（Phase 6 の stale 回収に統合済みなら、それを使う）
- ジョブストアの内容と現在の Playlist 設定を突き合わせ、**削除された Playlist のジョブを除去する**
- 設定変更時にジョブを再登録する

---

# 17. 手動実行との共存

- UI・CLI からの手動実行と、スケジュールによる自動実行が競合しないこと
- **同一 Playlist に対する discover / download の並行実行を禁止する**（要件定義 §8.3。既存の排他があればそれを使う）
- 手動実行中にスケジュールが発火した場合、スキップして記録する

---

# 18. レビュー③

記録は `docs/reviews/phase12.md`。レビュー②が指摘なしだった場合も**省略しないこと。**

**特に見てほしい観点**：

- **スケジューラが `app` でのみ動いているか**（worker で動く経路がないか）
- タイムゾーンの変換が一箇所に集約されているか
- 日をまたぐ時間帯指定が正しく扱われるか
- misfire で大量のジョブが積み上がらないか
- 削除された Playlist のジョブが除去されるか
- 手動実行とスケジュール実行が競合しないか
- **ホストの cron / systemd に依存していないか**
