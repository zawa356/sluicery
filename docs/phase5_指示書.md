
- `10\.[0-9]+\.` はバージョン番号（`10.5.` 等）に誤ヒットする。オクテットを4つ揃える形にする
- IPv6、`.local` / `.lan` / `.internal` のホスト名を検査対象に加える

# 2. 共通 Runner 基底クラスの切り出し

## 2.1 方針

Phase 3 の `YtdlpRunner` には、外部プロセス実行の汎用部分と yt-dlp 固有部分が混在している。rclone 用に同じものを書き直すのは無駄であり、かといって `YtdlpRunner` を汎用化して共用すると、**yt-dlp の進捗パースやエラー分類が rclone に持ち込まれて双方が汚れる。**

**共通部分を基底クラスに切り出し、`YtdlpRunner` と `RcloneRunner` がそれぞれ継承する構成にする。**

## 2.2 基底クラスに置くもの

`src/sluicery/runner/base.py`（新設。配置は実装判断でよいが、`downloader/` の下には置かない）

- `subprocess` の起動（`shell=True` 不使用、`start_new_session=True`）
- 環境変数の明示的構築（親環境を継承しない）
- **プロセスグループ単位の終了**（`os.killpg`、SIGTERM → 猶予 → SIGKILL）
- stdout / stderr の並行読み取り
- 無進捗タイムアウト・絶対タイムアウト・キャンセル
- stderr のログファイル出力と末尾保持
- **コマンドラインのマスク層**

## 2.3 サブクラスに残すもの

| クラス | 固有部分 |
|---|---|
| `YtdlpRunner` | `LC_ALL=C` の固定、`SLUICERY_PROGRESS` / `SLUICERY_PRINT` のフレーミング解釈、yt-dlp のエラー分類、`--print` による `--quiet` 補償 |
| `RcloneRunner` | `--use-json-log` の解釈、rclone のエラー分類、クレデンシャルの環境変数注入 |

## 2.4 リファクタの注意

**既存の `YtdlpRunner` の振る舞いを変えないこと。** Phase 3 の実機検証で確認済みの挙動（プロセスグループ終了、孤児プロセスを残さない、マスク）が壊れていないことを、既存テストで確認する。

テストが落ちた場合、**リファクタの誤りを疑う。テストを修正して通すのは最後の手段。**

# 3. RcloneRunner

`src/sluicery/storage/rclone.py`（またはこれに準ずる配置）。

## 3.1 出力の解釈

rclone は `--use-json-log` で構造化ログを出力できる。yt-dlp のようなプレフィックス規約を自前で作る必要はない。

- `--use-json-log` と `--log-level INFO`（進捗が要る場合は `--stats` と併用）を基本とする
- JSON 行のパースは、Phase 3 の `progress.py` と同様に**壊れた入力で例外を投げない**こと
- 進捗イベントの型は yt-dlp のものと共通化しない（意味が違う）。転送用に別途定義する

## 3.2 リトライの方針

**rclone 自身のリトライとアプリ側の Task リトライを二重にしない。**

- rclone 側は控えめに（`--retries 1` 程度）
- 実質的なリトライは**アプリ側の Task リトライに委ねる**（Phase 6/8）
- 二重リトライは失敗の検知を遅らせ、`blocked` 判定のタイミングを狂わせる

この判断を `docs/基本設計.md` に記録すること。

## 3.3 タイムアウト

転送は yt-dlp のダウンロードと性質が似ているため、同じ二段構えとする。

| 種別 | 設定キー | 既定 |
|---|---|---|
| 無進捗タイムアウト | `storage.idle_timeout_sec` | 300 |
| 絶対上限 | `storage.absolute_timeout_sec` | 21600 |
| 接続テスト用の全体タイムアウト | `storage.test_timeout_sec` | 30 |

接続テストは短く切ること。UI から呼ばれる操作（Phase 10）で長時間ブロックさせない。

## 3.4 対話の抑止

`--ask-password=false` 相当の指定により、**認証情報が不足した場合に対話待ちで固まらないこと**を保証する。実機で確認すること。

# 4. StorageAdapter インターフェース

要件定義 §14.4 のインターフェースを確定させる。

```python
class StorageAdapter(Protocol):
    def test_connection(self) -> ConnectionTestResult: ...   # §8
    def publish(self, src: Path, dest_rel: str) -> PublishResult: ...  # §9
    def exists(self, rel: str) -> bool: ...
    def list_recursive(self, rel: str) -> Iterator[RemoteFile]: ...
    def move(self, src_rel: str, dest_rel: str) -> None: ...
    def free_space(self) -> int | None: ...
```

## 4.1 補足

- `list_recursive()` は Phase 13（relink の再走査）で使う。**Phase 5 では実装するが、呼び出し元はまだない**
- `move()` は Phase 11（Playlist 名変更に伴うフォルダ移動）で使う。同上
- `free_space()` は取得できない場合 `None` を返す（§11）
- **相対パスは常に Storage ルートからの相対**とする。絶対パスを受け取らない
- パス traversal（`..`）を含む相対パスを拒否すること。Phase 4 の `layout/` で検証済みでも、**アダプタ層でも再検証する**（多層防御）

## 4.2 ファクトリ

`storage` レコードの `kind` からアダプタを生成する。

- `local` → `LocalStorageAdapter`
- `remote` → `RcloneStorageAdapter`
- `mount` → **明示的に「未実装」を返す**（§12）

# 5. local アダプタ

## 5.1 実装

`${MEDIA_ROOT}` の bind mount 配下（コンテナ内では `/mnt/media`）への直接書き込み。

**`MEDIA_ROOT` 環境変数の値をパスとして使わないこと**（D-010）。コンテナ内では常に `/mnt/media` 固定。

`storage.config_json` の `path` は、`/mnt/media` 配下の相対パスまたは絶対パスとして扱う。**`/mnt/media` の外を指すパスを拒否すること。**

## 5.2 接続テスト

`local` でも4段階の枠組みに乗せる。

| 段階 | local での意味 |
|---|---|
| 疎通 | パスが存在する |
| 認証 | （該当なし。常に成功として扱い、その旨を結果に含める） |
| 一覧 | ディレクトリを読める |
| 書き込み | テストファイルの作成・読み出し・削除ができる |

「該当なし」を「成功」と区別できるようにすること。UI（Phase 10）で誤解を招かない表示ができる。

# 6. remote（rclone）アダプタ

## 6.1 対応プロトコル

`storage.config_json` の `protocol` で分岐する。**Phase 5 で実機検証するのは SMB のみ。**

他プロトコル（NFS / WebDAV / SFTP / S3 等）は、設定項目の受け口を用意してよいが、**検証していないものを「対応済み」とドキュメントに書かないこと**（Phase 3.5 の方針を継続）。

## 6.2 リモート名

rclone のリモート名は、ユーザーが入力した Storage 名から直接作らない。**`storage.id` から機械的に導出**する（例：`st<id>`）。

理由：ユーザー入力には環境変数名に使えない文字が含まれうる。また名前変更でリモート名が変わると混乱する。

## 6.3 転送コマンド

- 単一ファイルの転送は `rclone moveto` または `copyto` を使う。`move` / `copy` はディレクトリ単位の挙動なので、**単一ファイルの publish には使わない**
- 転送先のディレクトリは必要に応じて作成する（`rclone mkdir`、または `copyto` の暗黙作成に依存するかを実機で確認する）

# 7. クレデンシャル管理

## 7.1 受け渡し方式：環境変数

**rclone の設定ファイルを生成しない。** `RCLONE_CONFIG_<REMOTE>_<KEY>` 形式の環境変数で渡す。

```
RCLONE_CONFIG_ST1_TYPE=smb
RCLONE_CONFIG_ST1_HOST=...
RCLONE_CONFIG_ST1_USER=...
RCLONE_CONFIG_ST1_PASS=<obscured>
```

理由：

- ファイルが生成されないため、クリーンアップの考慮が不要
- プロセス終了とともに消える
- tmpfs への書き込み・権限設定・競合の考慮が不要になる

要件定義 §6.5 の「rclone 設定ファイルは tmpfs 上に生成」は**この方式で置き換える**。要件からの変更として `docs/基本設計.md` に記録すること。

## 7.2 絶対に守ること

- **コマンドライン引数にクレデンシャルを載せない。** `ps` で他プロセスから見える
- 環境変数は `RcloneRunner` が起動するプロセスにのみ渡す。アプリ本体の環境を汚さない
- ログ・エラーメッセージ・CLI 出力は既存のマスク層を通す
- **`RCLONE_CONFIG_*` 環境変数名そのものもマスク対象に加える**（値だけでなく、変数名から Storage 構成が推測されうる）

## 7.3 パスワードの obscure（要確認）

rclone の設定値のパスワードは平文ではなく obscure 形式を要求する。`rclone obscure` サブコマンドで変換できるが、**引数として渡すと `ps` で平文が見える。**

**stdin 経由で渡す方法があるかを実機で確認し、無ければ代替手段を検討すること。** 確認結果と採用した方式を `docs/基本設計.md` に記録する。

## 7.4 DB への保存

Phase 2 の `EncryptedJSON`（Fernet）を使う。`storage.credentials_encrypted` に保存する。

- UI / CLI では write-only。設定後は「設定済み」表示のみで平文を返さない
- 設定エクスポート（Phase 17）の対象外である前提を、コード内コメントに明記する

# 8. 接続テスト（4段階判定）

## 8.1 段階

| # | 段階 | 判定内容 |
|---|---|---|
| 1 | 疎通 | ホストに到達できる |
| 2 | 認証 | 認証情報が受け入れられる |
| 3 | 一覧 | 対象パスのディレクトリ一覧を取得できる |
| 4 | 書き込み | テストファイルの作成・読み出し・削除ができる |

**各段階を個別に判定して結果を返すこと。** 「どこで失敗したか」が分かることが要件（§6.4）。

## 8.2 判定方法

rclone は終了コードだけでは4段階を区別しない。**stderr / JSON ログのパターンマッチが必要**になる。

Phase 3 の `downloader/errors.py` と**同じ設計を適用する**（ルールテーブルを一箇所に集約、未知は安全側に倒す）。ただし**分類の意味が違うため、コードは共通化しない。** パターンだけ真似る。

## 8.3 テストファイルの後始末

書き込みテストで作成したファイルは**必ず削除する**。削除に失敗した場合、その旨を結果に含めてユーザーに知らせる（残骸を黙って放置しない）。

ファイル名は衝突しないもの（UUID を含む等）とし、既存ファイルを上書きしないこと。

## 8.4 結果の保存

`storage.last_check_at` / `last_check_result_json` に記録する。CLI / UI から再実行できる。

# 9. publish の原子性（最重要）

## 9.1 原則

**転送が中断されたとき、中途半端なファイルが最終保存先に残ってはならない。**

Phase 7 のパイプラインが乗る土台であり、ここが甘いと不完全ファイルがライブラリに混入する。

## 9.2 手順（両アダプタで統一）

```
1. 一時名で転送する          <dest>.sluicery-tmp-<uuid>
2. 転送完了を確認する         （サイズ照合。可能ならチェックサム）
3. 最終名へ rename する       原子的
```

- **local**：同一ファイルシステムなら `os.replace`。異なる FS をまたぐ場合も、一時名で書いてから rename する
- **remote**：rclone の転送は原子的でないため、一時名へ転送してから `rclone moveto` でリモート上の rename を行う

## 9.3 既存ファイルの扱い

同名ファイルが既に存在する場合の挙動を決めること。

推奨：**既定では上書きしない**（設計原則1「ローカルのデータを失わない」）。上書きが必要な場面（Phase 7 の再取得等）は、呼び出し側が明示的に指定する引数を用意する。

## 9.4 中断された一時ファイルの掃除

`.sluicery-tmp-*` が残った場合の扱いを決めること。

推奨：**自動削除しない。** 検出して報告する（Staging の孤立ファイルと同じ方針、要件定義 §6.3）。`storage` に対する掃除コマンドを CLI に用意してもよいが、確認を挟むこと。

## 9.5 検証

**転送中に中断させて、最終保存先に不完全ファイルが残らないことを実機で確認する**（§16）。ユニットテストでは再現しにくい。

# 10. Storage のエラー分類

`src/sluicery/storage/errors.py`。

## 10.1 分類

| 分類 | 意味 | Phase 6/8 での扱い |
|---|---|---|
| `ok` | 成功 | — |
| `failed` | 一時的な失敗 | リトライ対象 |
| `unreachable` | ホストに到達できない | **`blocked` 相当。リトライ回数を消費しない** |
| `auth_failed` | 認証失敗 | 設定の誤りであり、リトライしても直らない。ユーザーへの通知が必要 |
| `no_space` | 容量不足 | **`blocked` 相当** |
| `permission_denied` | 書き込み権限がない | 設定の問題 |

**未知のエラーは `failed`（安全側）に倒す**（D-014 と同じ原則）。

## 10.2 Target 状態への対応

Phase 8 で `target.status` へ写像する。Phase 5 では**分類を返すところまで**とし、状態遷移は行わない。

対応の目安を `docs/基本設計.md` に記録しておくこと（Phase 8 の実装者への申し送り）。

# 11. 空き容量と閾値

## 11.1 取得

`rclone about` はバックエンドによって対応状況が異なる。**SMB で取得できるかを実機で確認すること。**

取得できない場合は `None` を返す。

## 11.2 `None` の場合の挙動

**容量チェックをスキップし、「容量取得不可」として記録・表示する。** 取得できないことを理由に転送を止めない。

止める設計にすると、対応していないバックエンドで一切動かなくなる。

## 11.3 閾値

要件定義 §6.4 に従い、空き容量が閾値を下回った Storage を publish 先とする処理を `blocked` にする。Phase 5 では**判定関数を用意するところまで**とし、Task への反映は Phase 6/7。

設定キー（`CODE_DEFAULTS` に追加）：

| キー | 既定 |
|---|---|
| `storage.free_space_warn_bytes` | 10 GiB |
| `storage.free_space_stop_bytes` | 2 GiB |
| `storage.idle_timeout_sec` | 300 |
| `storage.absolute_timeout_sec` | 21600 |
| `storage.test_timeout_sec` | 30 |
| `storage.rclone_retries` | 1 |

`StorageKind` に `mount` は既に存在するが、**Phase 5 では実装しない。**

# 13. CLI の拡張

## 13.1 Storage の remote 対応

Phase 4 では `--kind local` のみ受け付けていた。`remote` を追加する。

```
sluicery storage add --kind remote --name <名前> \
  --protocol smb --host <ホスト> --share <共有名> --path <相対パス> \
  --user <ユーザー名> [--domain <ドメイン>]
```

**パスワードは引数で受け取らない。** 対話プロンプト（`getpass`）または標準入力から受け取る。引数で渡すとシェル履歴と `ps` に残る。

`--password-stdin` のような明示的なフラグを用意してもよい。

## 13.2 検証用コマンド

```
sluicery storage test <name|id>              接続テスト（4段階の結果を表示）
sluicery storage space <name|id>             空き容量を表示（取得不可なら明示）
sluicery storage ls <name|id> [<rel-path>]   一覧
sluicery storage push <name|id> <local-path> <dest-rel>   単一ファイルの publish
```

`push` は **Phase 7 のパイプラインが入るまでの暫定実装**であることをコード内コメントと README に明記する。

## 13.3 出力

- 接続テストの結果は4段階を個別に表示する
- **クレデンシャルは既存のマスク層を通す**
- `storage show` にクレデンシャルの平文を出さない（「設定済み」表示のみ）

# 16. 実機検証（SMB 環境）

## 16.1 検証環境の準備（ユーザー側）

以下をユーザーに用意してもらう。**準備できるまで実機検証に着手しない。**

- LAN 上の SMB サーバー（Samba 等）
- **本検証専用の共有**（既存の共有を使わない）
- **本検証専用のユーザーアカウント**（使い捨てのパスワード）
- 書き込み権限のある共有と、**読み取り専用の共有を1つずつ**（権限エラーの検証用）

## 16.2 記録に関する厳守事項（重要）

**実ホスト名・IP アドレス・共有名・ユーザー名・パスワードを、いかなるドキュメントにも書かないこと。**

Phase 3.5 で AISTATE に実 IP が混入し、履歴の修正が必要になった前例がある。

- 検証記録には `<SMB_HOST>` / `<SHARE>` / `<USER>` のプレースホルダを使う
- コマンド例も同様
- `.env` や DB に入れた実値はコミット対象外であることを確認する
- **検証完了後、`docs/公開前チェックリスト.md` の監査（§0.1 で修正したもの）を再実行する**

検証終了後、共有とアカウントの削除はユーザーの判断に委ねる。

# 21. 実装時の注意（再掲）

- **未知のエラーは `failed`。** 安全側に倒す

- **`mount` の空実装クラスを作らない**
- **検証していないプロトコルを「対応済み」と書かない**
- **実ホスト名・IP・共有名・ユーザー名をドキュメントに書かない**（Phase 3.5 の前例）
- **`MEDIA_ROOT` 環境変数の値をパスとして使わない**（D-010）
- 判断に迷ったら要件定義 §1.4 の設計原則に照らし、それでも決まらなければ**確認を取る**
