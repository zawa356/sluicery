# Part A — Phase 13：整合性チェックと relink

**本フェーズは設計原則1に最も近い。慎重に実装すること。**

# 3. relink

## 3.1 目的

ユーザーはエクスプローラー等から**ファイルを移動・リネーム・削除する**。パスの存在確認だけでは移動を削除と誤認する（要件定義 §11.3）。

## 3.2 手順

```
1. artifact.relative_path の実在を確認
2. 見つからない場合、同一 Storage 配下を [<source_id>] で再走査
3. 発見したら DB のパスを更新（relink）。ファイルは動かさない
4. 再走査でも見つからない場合のみ missing_since を記録し、target を missing に
```

## 3.3 絶対に守ること

- **整合性チェックは読み取り専用である。** いかなる場合もファイルを削除・移動しない
- 再走査で複数の候補が見つかった場合、**自動で選ばず、手動リンクの対象として報告する**
- 走査中にエラーが起きた場合、**`missing` と判定しない**（Storage 到達不能を削除と誤認しない）

## 3.4 走査コストの制御（重要）

`list_recursive()` を remote Storage に対して毎回実行すると、SMB 越しの全走査は重い。

**方針：**

- **パス確認（手順1）は全 Artifact に対して行う。** これは軽い
- **再走査（手順2）は、パス不在の Artifact が存在する場合にのみ、Storage 単位で1回だけ行う**。Artifact ごとに走査しない
- 走査結果を一時的に保持し、同一実行内で使い回す
- 走査結果を永続キャッシュしない（ファイルシステムの変化に追従できなくなる）

| 設定キー | 既定 |
|---|---|
| `integrity.rescan_timeout_sec` | 600 |
| `integrity.max_candidates_per_source_id` | 5 |

走査がタイムアウトした場合、**`missing` 判定を行わずに中断する**（誤判定を避ける）。

## 3.5 実行経路

- CLI：`sluicery integrity check [--storage <name>] [--playlist <name>]`
- UI：整合性レポート画面から手動実行
- スケジューラ：Phase 12 の app スケジューラに integrity check の cron を登録する（既定日次）

**ジョブ引数に秘密値やパスを保存しないこと**（Phase 12 の方針）。

# 4. missing の扱い

Playlist 単位で選択する（要件定義 §11.3）。

| 選択肢 | 動作 |
|---|---|
| 放置（**既定**） | 状態を記録するのみ |
| 再取得 | Target を `pending` に戻す |
| 無視 | Target を `ignored` にし、以後の処理対象から外す |

**自動再取得は既定で無効。** オプトインとする。

`missing` から復帰した場合（ユーザーがファイルを戻した等）、次回の整合性チェックで `downloaded` に戻す。

# 5. 手動リンク画面

## 5.1 目的

ユーザーがリネームで `[<source_id>]` を消した場合、relink できない。その救済（要件定義 §11.3）。

## 5.2 画面

- **Storage 配下の未追跡ファイル一覧**（孤立ファイル）
- **`missing` な Target の一覧**
- 両者を並べ、手動で対応付ける

## 5.3 対応付けの動作

- **DB のパスを更新するのみ。ファイルは動かさない**
- 対応付け後、`target.status` を `downloaded` に戻す
- 誤った対応付けを取り消せること（`missing` に戻す）

## 5.4 孤立ファイルの検出

Storage 配下のファイルのうち、どの Artifact にも紐づかないもの。

- **自動削除しない。** 一覧表示のみ
- `/data/staging/trailer_1080p.mov`（Phase 3 由来）は Staging であり Storage ではないので、この対象ではない（Phase 7 の `staging orphans` が扱う）

# 10. yt-dlp 自動更新（Phase 15）

## 10.1 重要度が上がっている

Phase 12 の 403 対処で、**yt-dlp は JS ランタイム要件のような破壊的変更を挟む**ことが分かった。単にバージョンを上げるだけでは、更新後に静かに壊れる。

## 10.2 スモークテスト（強化）

要件定義 §5.3 は `--simulate` によるスモークテストを求めているが、**それでは不十分である。**

**以下を含めること。**

| # | 検証内容 |
|---|---|
| 1 | `yt-dlp --version` が動く |
| 2 | **JS ランタイム（Deno）が検出される** |
| 3 | `--simulate` でメタデータが取得できる |
| 4 | **実際に1本ダウンロードできる**（小さい CC 素材） |
| 5 | **`n challenge solving failed` の警告が出ていない** |
| 6 | メタデータ・サムネイルの埋め込みが動く（`yt-dlp[default]` の extras、D-023） |

スモークテスト用の URL は `ytdlp.smoketest_url`（既定は D-015 の Blender 素材）。

**#4 のダウンロードは Staging に落として検証後に削除する。** Storage には publish しない。

## 10.3 ロールバック

Phase 3 のバージョン切替機構（symlink）を使う。

- スモークテスト失敗 → **直前バージョンへ自動ロールバック**
- ロールバック後、再度スモークテストを行い、旧バージョンが健全であることを確認する
- **旧バージョンでも失敗する場合、ロールバックせずに状態を報告する**（両方壊れているなら、新しい方が直る見込みが高い）
- `run_failed` フックを発火する

## 10.4 スケジュール

Phase 12 の app スケジューラに登録する。既定は週次。無効化も可能。

## 10.5 UI

- 現在バージョン、最終更新日時、最終スモークテスト結果
- 手動更新ボタン、手動ロールバックボタン
- 更新履歴（`ytdlp_release` テーブル、Phase 3 で作成済み）

## 10.6 Deno の更新

**Deno はイメージに焼き込まれているため、自動更新の対象外。** yt-dlp の更新で Deno のバージョン要件が変わった場合、スモークテストの #2・#5 で検出される。

その場合の対処（Dockerfile の `DENO_URL` / `DENO_SHA256` を更新して再ビルド）を `docs/troubleshooting.md` に書くこと。

# Part C — Phase 16-18：retention・エクスポート・フック

# 12. retention（Phase 16）

**これは唯一の「ファイルを削除する機能」である。最も慎重に実装すること。**

## 12.1 既定

**無効。** 有効化しない限り一切動作しない。

## 12.2 ポリシー

Playlist 単位で設定する。

| 種別 | 内容 |
|---|---|
| 件数 | 最新N件のみ保持 |
| 期間 | M日より古いものを削除 |

## 12.3 ドライラン必須（要件定義 §11.6）

- **有効化時と実行時の両方でドライランを必須とする**
- 削除対象の一覧（パス、サイズ、日付）を表示する
- **確認を経なければ実行しない**
- UI では二段確認（チェックボックス + 確認ボタン）

## 12.4 安全装置（本書で追加する要件）

要件定義には無いが、**削除は取り消せないため以下を実装すること。**

| 装置 | 内容 |
|---|---|
| 件数上限 | 1回の実行で削除できる件数に上限を設ける（`retention.max_delete_per_run`、既定20）。超える場合は実行を拒否し、ユーザーに分割を促す |
| 割合ガード | Playlist の Artifact の**過半数を削除しようとする場合は拒否**する。設定ミスの検出 |
| ドライラン結果の有効期限 | ドライランから実行までに時間が空いた場合、再確認を求める（`retention.dryrun_ttl_sec`、既定300） |
| 削除ログ | 削除したファイルのパス・サイズ・日時を**必ずログに残す**（復旧はできないが、何が消えたかは追える） |

**これらを追加した理由を `docs/基本設計.md` に記録すること。**

## 12.5 削除後の状態

削除された Artifact に対応する Target は **`ignored`** にする（要件定義 §11.6）。再取得の対象にしない。

## 12.6 delisted との関係

**retention と差分レポート（§6）は別機能である。**

- 差分レポート：配信元から消えた Item の一覧。**削除機能を持たない**
- retention：ユーザーが明示的に設定した保持ポリシー

混同させないこと。UI 上でも別画面にする。

# 13. 設定エクスポート / インポート（Phase 17）

## 13.1 対象

Playlist、Profile、playlist_profile、Storage（**クレデンシャル除外**）、グローバル設定。

**対象外：** Item / Target / Artifact / Run / Task などの実行状態、`_internal.*` の内部キー、Cookie。

## 13.2 形式

YAML 単一ファイル。

## 13.3 インポート

- **差分プレビューを表示し、確認を経てから適用する**
- クレデンシャルを要する項目は「要再入力」として提示する
- 既存レコードとの衝突時の挙動（スキップ / 上書き / 新規作成）を選べること
- **インポートがファイルを削除・移動しないこと**

## 13.4 用途

リポジトリに commit しておけば環境再構築時に流し込める、という運用を想定（要件定義 §15）。

**エクスポート結果に秘密が含まれないことをテストで保証すること。**

# 14. フック機構（Phase 18）

## 14.1 スコープ

**インターフェースと `event_log` への記録のみ。** 具体的なアダプタ（Jellyfin / Navidrome / Webhook）は実装しない（要件定義 §14.1）。

## 14.2 イベント

```
item_discovered, item_delisted,
target_downloaded, target_failed,
run_started, run_finished, run_failed,
artifact_published, artifact_missing,
storage_unreachable, ytdlp_updated, ytdlp_rollback
```

Phase 7 で `index` タスクからの発火点を設置済み。**残りのイベントの発火点を追加する。**

## 14.3 要件

- `config/hooks.yaml` で購読側を有効化する
- **発火は非同期。フックの失敗が本体処理に影響しない**
- 現バージョンでは `event_log` への記録のみを行う組み込みフックを1つ用意する
- **ペイロードに秘密値・URL・Cookie を含めない**

## 14.4 将来の拡張

`config/hooks.example.yaml` に、将来 Jellyfin / Navidrome を追加する際の設定例をコメントとして書いておく。**実装はしない。**

```yaml
  - apparmor:unconfined
```

**既定では無効。** 明示的にオーバーレイを指定した場合のみ有効になる。

## 16.2 `mount` アダプタ

`StorageAdapter` の `mount` kind を実装する。

- `mount -t cifs` / `mount -t nfs` をコンテナ内で実行する
- **`compose.privileged.yaml` が有効な場合のみ UI の選択肢に出る**
- 無効な場合、Phase 5 と同じく「未実装/利用不可」を明示的に返す

## 16.3 実機検証の制約

**外部検証 VM への SSH が拒否されている（未解決 #6）ため、`mount` kind の実機検証は困難である。**

**方針：実装とユニットテストまでを行い、実機未検証であることを明記する。**

- `docs/storage.md` に「実装済みだが実機未検証」と正直に書く
- README の検証状況にも反映する
- ローカル Docker で試せる範囲（コンテナ起動、cap の付与確認、マウント試行のエラーハンドリング）は検証する
- **検証していないものを検証済みと書かない**（既存の方針）

## 16.4 GPU 設定

`compose.yaml` に NVENC 用のコメントアウト設定は Phase 1 で配置済み。**内容が現在の構成と整合しているか確認するのみ。**

# 17. バックアップ / リストアと仕上げ（Phase 20）

## 17.1 `make backup`

要件定義 §9 の通り。対象：

- SQLite DB
- `config/`
- ログ（任意。設定で切り替え）

**含めないもの：** メディア本体、Staging、yt-dlp venv。

## 17.2 `SECRET_KEY` の扱い（重要）

バックアップにはクレデンシャルが**暗号化された状態で**含まれる。復号には `SECRET_KEY` が必要。

**方針：`SECRET_KEY` をバックアップに含めない。**

理由：含めると、バックアップファイル1つの流出で全クレデンシャルが復号可能になる。

代わりに、

- **バックアップ実行時に「`SECRET_KEY` を別途保管する必要がある」旨を警告表示する**
- リストア時に `SECRET_KEY` の指紋を照合し、不一致なら明確に警告する（Phase 2 の仕組みを使う）
- `docs/legal.md` と `docs/deployment.md` に明記する

**この判断を記録すること。**

## 17.3 `make restore`

- **既存データを上書きする前に確認を求める**
- リストア前に現状のバックアップを自動取得するか、少なくとも警告する
- **メディアファイルには一切触れない**
- リストア後、マイグレーションの適用状態を確認する

## 17.5 要件定義 §19 の総点検（最重要）

**要件定義 §19 の受け入れ条件26項目を、1つずつ実機で確認する。**
