# sluicery 基本設計

本書は「どう作るか（HOW）」を記録する。仕様の根拠（WHAT）は `docs/要件定義.md` を参照。
実装に合わせて随時更新する。

## 1. 全体構成図（サービス／データフロー）

                 │   Web ブラウザ       │
                 └─────────┬──────────┘

                 │  app                │        │  永続 volume   │
                 │  - FastAPI          │◄──────►│  /data         │
                 │  - Jinja2 + HTMX    │        │  - sqlite db   │
                 │  - APScheduler      │        │  - ytdlp-venv  │
                 └─────────┬──────────┘        │  - logs        │
                            │ Task 投入（DB経由）  └───────┬───────┘
        ┌───────────────────┴───────────────────┐         │

## 3. データモデル（実装スキーマと要件定義の論理設計との差分）

Phase 2 で要件定義 §7.1 の全12テーブルを実装した。論理設計との差分は以下の通り。

| 項目 | 差分 | 理由 |
|---|---|---|
| `TaskStatus` | `pending` / `queued` / `running` / `succeeded` / `failed` / `cancelled` として確定 | 要件定義は値を明記していなかった。§10.4「`running` のまま残った Task を `failed` に落とす」の記述と整合させた |
| `RunStatus`（新規） | `running` / `succeeded` / `failed` / `cancelled` | `run.status` カラムに要件定義が値を与えていなかったため新設。`TaskStatus` と異なり `pending`/`queued` は持たない（Run はキューに乗らず即時開始するため） |
| `task.created_at` | 追加（`updated_at` は追加せず） | 要件定義の論理設計にはないが、`claim_next()` の候補選定で `priority` 降順・`id` 昇順の同点タイブレークに ID の単調増加性を利用しており、実質的に FIFO を保証している。将来的に別途生成時刻が必要になった場合の保険としても追加 |
| `setting` の主キー | `key`（文字列）を主キーとし、`id` 列を持たない | 要件定義の論理設計自体が `key, value_json, updated_at` のみで `id` を持たない自然キー設計だったため、そのまま踏襲した。§4.6「主キーは整数 autoincrement」の原則の唯一の例外 |
| `user` の2件目禁止 | DB 制約ではなく `UserRepository.create_single()`（リポジトリ層）で担保 | `username` の `UNIQUE` 制約だけでは異なるユーザー名の2件目を防げない。SQLite で「テーブル全体で1行のみ」を宣言的に強制する簡潔な方法がないため、アプリ層でチェックする方式にした |
| タイムスタンプ型 | `DateTime(timezone=True)` ではなく独自の `UTCDateTime`（`TypeDecorator`） | SQLAlchemy + SQLite では `DateTime(timezone=True)` を指定しても tzinfo が書き込み時に無言で破棄され、読み出し時も naive datetime になる（テストで実際に発覚）。`UTCDateTime` は書き込み時に tz aware であることを検証して UTC に変換・保存し、読み出し時に `tzinfo=UTC` を明示的に付与することで §3.3 の方針を実際に満たす |
| `.env` → DB へ移した項目 | `STAGING_WARN_PCT` / `STAGING_STOP_PCT` / `LOG_RETENTION_DAYS` / `YTDLP_UPDATE_CRON` / `YTDLP_SMOKETEST_URL` に加え、`download.*` 系（`item_concurrency` 等、要件 §9.5）、`schedule.*`、`retry.max_attempts`、`ytdlp.*`（`auto_install` 等、Phase 3）を `setting` テーブル側の運用パラメータとして定義（`core/settings.py` の `CODE_DEFAULTS`） | 要件定義 §17 は `.env` に列挙していたが、docs/phase2_指示書.md §2.2 の方針（`.env` はセキュリティ境界とインフラ設定に限定）に従った |
| `ytdlp_release`（新規テーブル、Phase 3） | `id, version, installed_at, source(initial/manual/auto), status(installed/active/removed), activated_at, deactivated_at, smoketest_result_json, notes, created_at, updated_at` | 要件定義 §5.3 の「更新履歴（バージョン、日時、結果）を DB に記録する」に対応するテーブルが論理設計に無かったため新設（D-011） |
| `profile` の設定フラグ | `audio_extract` / `embed_metadata` / `embed_thumbnail` / `embed_chapters` / `subtitle_auto` / `subtitle_embed` を nullable に変更 | 要件定義 §7.1 は三状態を明示していないが、オプション合成で「未設定（継承）」と明示的な `false` を区別するため（D-017） |

**検討事項（未決定）**: 要件定義 §7.2 の `target.status` には `blocked`（外的要因で保留、`retry_count` を消費しない）があるが、`TaskStatus`（本書表の1行目）には対応する値が無い。Phase 6/7 で Storage 到達不能等により Task を保留する際、Task 側でどう表現するか（`blocked` を追加するか、`Target` 側の状態だけで表現し `Task` は単に `queued` のまま止めるか）は未決定。着手時に判断し、本表に追記すること。

## 4. 主要なフローのシーケンス（同期・パイプライン・relink）

### 4.1 yt-dlp venv のインストール（`downloader/version.install()`）

```
app (CLI/自動導入スレッド)
  │
  ├─ fcntl.flock(.lock) を取得（app のみ書き込み。worker は読み取り専用）
  ├─ [--version 指定 かつ --force 無し かつ 導入済み] なら
  │    └─ 現在 not_installed/broken なら active 化して早期リターン
  │       それ以外はそのまま早期リターン（何もしない）
  ├─ versions/.tmp-<uuid>/ に python -m venv
  ├─ pip install "yt-dlp[default]"（バージョン指定時は "yt-dlp[default]==<version>"）
  ├─ venv に導入契約マーカー（yt-dlp-default-extras-v1）を記録
  ├─ bin/yt-dlp --version で実際の導入バージョンを確認
  ├─ versions/<version>/ にリネーム（同名が既に有れば .tmp を破棄し既存を採用）
  ├─ ytdlp_release レコードを作成/更新
  └─ [current が無かった場合のみ] current を新バージョンに切替え、
       DB 上の active を1件に保つ（旧 active があれば installed に戻す）

失敗時: .tmp を確実に削除し、current・DB は一切変更しない
```

`get_status()` は実行ファイルだけでなく導入契約マーカーも確認する。Phase 3 までの本体のみの
venv や将来の契約変更は `broken` と判定し、自動導入が同一バージョンでも venv を再構築する。

### 4.2 バージョン切替（`downloader/version.use()`）

```
app
  ├─ fcntl.flock(.lock)
  ├─ 対象バージョンの導入確認（未導入なら UnknownVersionError）
  ├─ os.symlink(target, tmp_link) → tmp_link.replace(current)（原子的差替え）
  └─ DB: 旧 active → installed（deactivated_at 記録）、新対象 → active（activated_at 記録）
```

worker は `current` symlink 越しに `bin/yt-dlp --version` を読むだけで、
上記のいずれにも関与しない（§2.4）。

### 4.3 yt-dlp オプション合成

```
setting の download.*（L2） ─┐
setting の defaults.<kind>.*（L3）
Profile 構造化値（L4）       ├─ None を継承として最終値を1つに解決
一時上書き（L6）             ┘
          ↓ FIELD_TO_ARGS で引数化
Profile.ytdlp_args（L4）→ Playlist.ytdlp_args（L5）→ 一時自由入力（L6）を層順連結
          ↓ 予約引数ガード・警告収集
アプリ予約引数（L1）を最後に注入 → 単一 source_url
```

- 構造化値は最終値だけを出力し、勝った層・由来・フィールド名を `ArgumentOrigin` に保持する
- 自由文字列は `shlex.split` 後も元のトークン順を維持し、同一オプションは後段の層を yt-dlp の後勝ちで優先する
- discover はレート制御、Playlist 自由入力、`--flat-playlist` / `--simulate` / 識別情報 print だけを使い、レイアウト引数を含めない
- download は構造化値、ファイル名方針、自由入力の後に、Staging の `--paths`、相対 `--output`、進捗・after_move print を注入する

### 4.4 レイアウトと Staging パスの解決

```
playlist_profile.subpath（{playlist.*} / {profile.*}）
  → 変数展開 → NFC / Windows互換化 → 絶対パス・.. を拒否
  → flat または custom の yt-dlp 出力テンプレートを連結
  → <STAGING_DIR>/<work-id>/<subpath>/<filename>
```

subpath の `{...}` はアプリ独自構文、ファイル名の `%(...)s` は yt-dlp 構文であり、同じ段階では展開しない。Phase 7 の publish は work root からの相対パスをそのまま Storage に移す前提とする。

## 6. 外部依存（yt-dlp / rclone / ffmpeg）との境界

- yt-dlp: 永続 volume 上の venv に公式 `default` extras 付きでインストール。
  `mutagen`（音声メタデータ・サムネイル埋め込み）等も venv に含め、アプリイメージには焼き込まない
  （要件定義 §5）。導入契約マーカーで旧 venv を検出し、更新時に不足依存を自動修復する
- rclone / ffmpeg: イメージに焼き込む。バージョンは Dockerfile 内で明示固定
- いずれも CLI を subprocess 経由で呼び出す。Python API・shell 経由の呼び出しは行わない
- yt-dlp との出力プロトコル（Phase 3）:
  - `--progress-template "download:SLUICERY_PROGRESS %(progress)j"` で進捗を JSON 行として出力させる
  - `--print "[WHEN:]SLUICERY_PRINT %(...)"`（`%()j` で info dict 全体を JSON 化できる）でメタデータ・
    保存パス等を出力させる。`WHEN` は `--use-postprocessor` と同じ値が使える（`after_move` 等）
  - 上記2つの行頭プレフィックスで stdout を demux する（`downloader/protocol.py`）。プレフィックスの
    無い行は無視する
  - ロケールは `LC_ALL=C` に固定（エラー分類が英語メッセージに依存するため）
  - 子プロセスは新しいプロセスグループで起動し、タイムアウト・キャンセル時はグループ単位で終了させる
    （yt-dlp が子プロセスとして起動する ffmpeg が孤児化しないようにする）
  - 実機（yt-dlp 2026.07.04）で上記テンプレート構文の出力を確認済み
- ファイル名境界（Phase 4、yt-dlp 2026.07.04 で実測）:
  - `--windows-filenames` は `\ / : * ? " < > |` を削除せず、見た目の近い Unicode 文字
    （`⧹ ⧸ ： ＊ ？ ＂ ＜ ＞ ｜`）へ置換した。日本語と絵文字は保持された
  - Windows 予約語そのもの（`CON.mov`）と、拡張子直前のタイトル由来のドット・空白
    （`末尾. .mov`）は残った。ただし sluicery の標準テンプレートは末尾に `[<source_id>]`
    を必須とするため、生成される完全な stem が `CON` 等になることはない
  - `--trim-filenames` はテンプレート末尾の ID まで切り詰めうるため、flat のタイトル部分を
    120 byte に制限した上で使用する。ユーザー入力のディレクトリ要素は `core/naming.py` が
    予約語・禁止文字・末尾ドット/空白を処理する（D-018）

## 7. 設計判断の記録

### D-001: 権限降格に gosu ではなく setpriv（util-linux）を使う

- 日付: 2026-08-08
- 背景: PUID/PGID/UMASK を実行時に反映するには、root で起動してからアプリユーザーに降格する必要がある（要件定義 N-5）
- 選択肢: (a) gosu を GitHub リリースから取得して固定 (b) su-exec（Alpine 系、Debian には無い） (c) util-linux 同梱の setpriv
- 決定: (c)。Debian slim イメージに標準で入っており、追加の外部バイナリ取得・checksum 管理が不要
- 影響: なし

### D-002: ffmpeg は静的ビルドを checksum 検証して導入する

- 日付: 2026-08-08
- 背景: 要件定義 §4.2 で rclone / ffmpeg のバージョンを Dockerfile 内で明示固定することが求められている。apt 経由だと Debian リポジトリの状態に依存し、後から同じバージョンを再現できない
- 選択肢: (a) apt-get install ffmpeg （バージョン追跡が困難） (b) johnvansickle.com の静的ビルドを sha256 固定して取得
- 決定: (b)。取得 URL 自体は「最新の release」を指す固定文字列だが、ビルド時に sha256 を検証するため、上流が更新されればビルドが失敗して気づける（無言で異なるバイナリが混入しない）
- 影響: バージョンを上げる際は `FFMPEG_SHA256` を手動で更新する必要がある
- 補強（2026-08-08）: 取得 URL を `ARG FFMPEG_URL` として build-arg 化した。johnvansickle は最新版を固定名で配布し、旧版はバージョン番号付きファイル名で `old-releases/` 配下に残し続けるため、上流ローテーションで checksum 不一致が発生した場合は `old-releases/` の versioned URL に `FFMPEG_URL` を差し替えるだけで、以前と同一バージョンを再取得できる（イメージの再現性が壊れない）

### D-003: requirements.lock はこのセッションでは生成できていない

### D-006: `Task.claim_next()` は単一 UPDATE ... RETURNING でアトミックに実装する

- 日付: 2026-08-08
- 背景: 複数ワーカー（プロセス）が同一 Task を同時に claim してはならない（要件 §8.3）
- 選択肢: (a) `BEGIN IMMEDIATE` で明示的に排他ロックを取ってから SELECT→UPDATE の2文で実装する (b) 候補選定（`WHERE status=queued ORDER BY priority DESC, id ASC LIMIT 1`）と `queued→running` への更新を単一の `UPDATE ... WHERE id IN (...) ... RETURNING` 文にまとめる
- 決定: (b)。PRAGMA で `journal_mode=WAL` と `busy_timeout=5000` を設定済みであり、SQLite は書き込みを直列化するため、単一 UPDATE 文自体がアトミックな排他になる。実装がシンプルで、明示的なロック管理（例外時の unlock 漏れ等）のリスクがない
- 影響: 20〜30スレッドが同一/複数 Task を奪い合う並行テストで二重 claim が発生しないことを確認済み（`tests/test_task_claim_next.py`）

### D-007: DB のタイムスタンプに独自の `UTCDateTime` 型を使う

- 日付: 2026-08-08
- 背景: SQLAlchemy の `DateTime(timezone=True)` は SQLite では tzinfo を保持しない（書き込み時に無言で破棄、読み出し時は naive datetime）。テスト作成中に発覚した
- 選択肢: (a) アプリ側が読み出し後に毎回 `.replace(tzinfo=UTC)` するルールを徹底する (b) `TypeDecorator` でカラム型自体に UTC の付け外しを組み込む
- 決定: (b)。(a) は徹底を人手に頼ることになり、忘れた箇所だけ naive datetime が混入する事故が起きやすい。カラム型に閉じ込めることで、モデル層を使う限り自動的に守られる
- 影響: 書き込み時に naive datetime を渡すと `ValueError` になる（`datetime.now(UTC)` 等、必ず aware で渡す必要がある）

### D-008: Alembic autogenerate は SQLite 上の CHECK 制約を正しく比較できない（既知の制限）

- 決定: (b)。`sluicery config check` で書き込み可否を可視化する要件（docs/phase2_指示書.md §2.2）は維持しつつ、実際に意味のあるパスを検証する

### D-012: yt-dlp の `install` は明示的な `use` がない限り `current` を切り替えない（初回導入時を除く）

- 日付: 2026-08-08

- 選択肢: (a) `install` は常に導入したバージョンを `current` にする (b) `install` は導入のみ行い、`current` が存在しない（未導入・`broken`）場合に限り自動で `active` にする

### D-013: yt-dlp 未導入でも `app` は起動し、`worker` は待機ループへ入る（degraded 起動）

- 日付: 2026-08-08
- 背景: yt-dlp の導入前に `app`/`worker` が起動できないと、初回セットアップで `docker compose up -d` しただけでは何も操作できない。また Phase 6 の Task キューが未実装の間、`worker` は実処理を持たず、そのまま終了すると `restart: unless-stopped` により再起動ループに入り、Docker の restart backoff が効き始めてしまう
- 選択肢: (a) yt-dlp が無ければ起動を拒否する (b) `app` は常に起動し、`ytdlp.auto_install` が true ならバックグラウンドで自動導入を試みる。`worker` は yt-dlp が `ready` になるまで待機ループに入り、終了しない
- 決定: (b)。`SECRET_KEY` 未設定時の拒否（設計原則上「即座に気づくべき致命的な設定ミス」）とは性質が異なり、yt-dlp 未導入は運用中に起こりうる正常な状態（自動更新失敗時のロールバック前など）として扱う
- 影響: 自動導入はベストエフォートであり、失敗しても `app` 自体はログを出すだけで動き続ける。`worker` の待機ループはログを初回と状態変化時のみ出す（毎ループ出力すると起動直後にログが埋まる）

### D-014: 未知の yt-dlp エラーメッセージは `failed`（安全側）に分類する

- 日付: 2026-08-08
- 背景: エラー分類ルール（`downloader/errors.py`）は yt-dlp の英語メッセージの部分一致に依存しており、バージョンアップで文言が変わると簡単に外れる
- 選択肢: (a) 未知のメッセージは `unavailable`（回復不能）に倒す (b) `blocked`（保留、リトライ回数を消費しない）に倒す (c) `failed`（一時的失敗、リトライ対象）に倒す
- 決定: (c)。`unavailable` に誤って倒すと自動リトライ対象から外れて放置される。`blocked` に誤って倒すとリトライ回数の上限がいつまでも効かなくなる。`failed` はリトライ回数を消費しつつ既定の上限（`retry.max_attempts`）で最終的に `unavailable` へ落ちるため、誤分類時の実害が一番小さい
- 影響: 実機で新しいエラーパターンを見つけるたびに `ERROR_RULES` へ追記していく運用になる

- 影響: 日付欠損時は `タイトル [id].ext`、番号欠損時は `0 トラック名 [id].ext` になる。yt-dlp 2026.07.04 の `--load-info-json` で欠損ケースを確認済み

### D-020: expert mode で指定された予約引数は対応する L1 注入を省く

- 日付: 2026-08-09
- 背景: expert mode の予約引数を許可しつつ同じ引数を L1 でも後置すると、実際には常にアプリ側が勝ち、許可した意味がなくなる。一方で両方を残すと preview とファイル追跡の解釈が曖昧になる
- 選択肢: (a) L1 を常に後勝ちさせる (b) expert 指定を検出した予約引数だけ L1 注入を省く
- 決定: (b)。canonical 名へ別名を解決した上で、`--paths` / `--print` / `--progress-template` の対応する L1 グループを省き、進捗・生成パス・ファイル追跡が壊れうる警告を `BuiltCommand` に記録する
- 影響: expert mode は意図どおり強力だが、警告を理解できる利用者向け。`--output` は expert mode でも自由入力を許可せず custom の正規経路だけを使い、`--download-archive` は状態管理源を分岐させるため常に拒否する。`--exec` 系は `ALLOW_EXEC` と Profile `allow_exec` の二重ゲートを別途必須とする

### D-021: 暫定 CLI の Playlist `--keep-items` はソフト削除とする

- 日付: 2026-08-09
- 背景: `item.playlist_id` は NOT NULL であり、Playlist レコードだけを削除して Item を孤立させることはできない。一方、Phase 4 指示書は Playlist 削除時に `--keep-items` / `--delete-items` の明示を求める
- 選択肢: (a) `--keep-items` でも Item DB レコードを削除してファイルだけ残す (b) Playlist を `enabled=false` / `paused=true` にして全関連レコードを保持する
- 決定: (b)。`--keep-items` はソフト削除、`--delete-items` は Playlist / Item / Target / Artifact / playlist_profile の DB レコード削除とする。どちらも実ファイル API を呼ばない
- 影響: `--keep-items` 後も Playlist は `list` / `show` に残り、再有効化できる。Run 履歴が参照する Playlist の物理削除は拒否する

### D-023: yt-dlp venv の実行依存を導入契約として管理する

- 日付: 2026-08-09
- 背景: yt-dlp 本体だけの venv では動画取得は通る一方、音楽 Profile のメタデータ・サムネイル埋め込みが `mutagen` 不足で postprocess 失敗した。コード更新前から存在する同一バージョンの venv は通常の auto install では no-op になり、依存追加が反映されない
- 選択肢: (a) アプリイメージの Python パッケージを venv へ露出 (b) 個別依存を独自列挙 (c) 公式 `default` extras とアプリ側の導入契約マーカーを使う
- 決定: (c)。`yt-dlp[default]` を venv に導入し、`.sluicery-install-contract` に契約バージョンを記録する。marker 不在・不一致、実行不能、またはディレクトリ名と `--version` の不一致は `broken` とする。検証は current だけでなく各バージョンディレクトリへ適用し、`use` は broken 版を拒否、`install` は既存の broken 版を一時 venv から再構築する
- 影響: Phase 3 までの venv は初回起動時に一度だけ自動再構築される。worker は再構築中 `broken` として待機し、current の原子的差替え後に `ready` へ復帰する。非 current の旧版も、切替前に再導入が必要になる
