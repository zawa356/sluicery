# sluicery 基本設計

本書は「どう作るか（HOW）」を記録する。仕様の根拠（WHAT）は `docs/要件定義.md` を参照。
実装に合わせて随時更新する。

## 1. 全体構成図（サービス／データフロー）

## 3. データモデル（実装スキーマと要件定義の論理設計との差分）

Phase 2 で要件定義 §7.1 の全12テーブルを実装した。論理設計との差分は以下の通り。

| 項目 | 差分 | 理由 |
|---|---|---|
| `TaskStatus` | `pending` / `queued` / `running` / `succeeded` / `failed` / `unavailable` / `blocked` / `cancelled` | Phase 6 で外的要因を試行回数を消費せず保留する `blocked` と、回復不能・試行上限到達を表す `unavailable` を追加（D-029） |
| `RunStatus`（新規） | `running` / `succeeded` / `failed` / `cancelled` | `run.status` カラムに要件定義が値を与えていなかったため新設。`TaskStatus` と異なり `pending`/`queued` は持たない（Run はキューに乗らず即時開始するため） |
| `task.created_at` | 追加（`updated_at` は追加せず） | 要件定義の論理設計にはないが、`claim_next()` の候補選定で `priority` 降順・`id` 昇順の同点タイブレークに ID の単調増加性を利用しており、実質的に FIFO を保証している。将来的に別途生成時刻が必要になった場合の保険としても追加 |
| `task.available_at` / `blocked_until` | nullable UTC datetime を追加 | 自身の一時失敗によるバックオフと外的要因による保留を区別する（D-032） |
| `task.blocked_reason` | nullable 文字列を追加 | Storage 等の外的要因の分類・理由を保持する |
| `task.heartbeat_at` / `worker_id` | nullable UTC datetime / 文字列を追加 | 実行所有者を明示し、応答不能 worker の stale Task を安全に回収する |
| `task.cancel_requested` | NOT NULL bool（既定 false）を追加 | CLI / 将来の UI から実行中 handler へ非同期キャンセルを伝える |
| `setting` の主キー | `key`（文字列）を主キーとし、`id` 列を持たない | 要件定義の論理設計自体が `key, value_json, updated_at` のみで `id` を持たない自然キー設計だったため、そのまま踏襲した。§4.6「主キーは整数 autoincrement」の原則の唯一の例外 |
| `user` の2件目禁止 | DB 制約ではなく `UserRepository.create_single()`（リポジトリ層）で担保 | `username` の `UNIQUE` 制約だけでは異なるユーザー名の2件目を防げない。SQLite で「テーブル全体で1行のみ」を宣言的に強制する簡潔な方法がないため、アプリ層でチェックする方式にした |
| タイムスタンプ型 | `DateTime(timezone=True)` ではなく独自の `UTCDateTime`（`TypeDecorator`） | SQLAlchemy + SQLite では `DateTime(timezone=True)` を指定しても tzinfo が書き込み時に無言で破棄され、読み出し時も naive datetime になる（テストで実際に発覚）。`UTCDateTime` は書き込み時に tz aware であることを検証して UTC に変換・保存し、読み出し時に `tzinfo=UTC` を明示的に付与することで §3.3 の方針を実際に満たす |
| `.env` → DB へ移した項目 | `download.*` / `schedule.*` / `ytdlp.*` / `storage.*` に加え、Phase 6 の `worker.*`（poll、heartbeat、stale、retry、progress、shutdown、検証用 Task の有効化）を `setting` テーブル側の運用パラメータとして定義 | `.env` はセキュリティ境界とインフラ設定に限定する D-005 に従った |
| `ytdlp_release`（新規テーブル、Phase 3） | `id, version, installed_at, source(initial/manual/auto), status(installed/active/removed), activated_at, deactivated_at, smoketest_result_json, notes, created_at, updated_at` | 要件定義 §5.3 の「更新履歴（バージョン、日時、結果）を DB に記録する」に対応するテーブルが論理設計に無かったため新設（D-011） |
| `profile` の設定フラグ | `audio_extract` / `embed_metadata` / `embed_thumbnail` / `embed_chapters` / `subtitle_auto` / `subtitle_embed` を nullable に変更 | 要件定義 §7.1 は三状態を明示していないが、オプション合成で「未設定（継承）」と明示的な `false` を区別するため（D-017） |

## 4. 主要なフローのシーケンス（同期・パイプライン・relink）

### 4.1 yt-dlp venv のインストール（`downloader/version.install()`）

```
app (CLI/自動導入スレッド)
  │
  ├─ fcntl.flock(.lock) を取得（app のみ書き込み。worker は読み取り専用）
  ├─ [--version 指定 かつ --force 無し かつ 導入済み] なら
  │    └─ 現在 not_installed/broken なら active 化して早期リターン
  │       それ以外はそのまま早期リターン（何もしない）
  ├─ versions/.tmp-<uuid>/ に python -m venv
  ├─ pip install "yt-dlp[default]"（バージョン指定時は "yt-dlp[default]==<version>"）
  ├─ venv に導入契約マーカー（yt-dlp-default-extras-v1）を記録
  ├─ bin/yt-dlp --version で実際の導入バージョンを確認
  ├─ versions/<version>/ にリネーム（同名が既に有れば .tmp を破棄し既存を採用）
  ├─ ytdlp_release レコードを作成/更新
  └─ [current が無かった場合のみ] current を新バージョンに切替え、
       DB 上の active を1件に保つ（旧 active があれば installed に戻す）

失敗時: .tmp を確実に削除し、current・DB は一切変更しない
```

`get_status()` は実行ファイルだけでなく導入契約マーカーも確認する。Phase 3 までの本体のみの
venv や将来の契約変更は `broken` と判定し、自動導入が同一バージョンでも venv を再構築する。

### 4.2 バージョン切替（`downloader/version.use()`）

```
app
  ├─ fcntl.flock(.lock)
  ├─ 対象バージョンの導入確認（未導入なら UnknownVersionError）
  ├─ os.symlink(target, tmp_link) → tmp_link.replace(current)（原子的差替え）
  └─ DB: 旧 active → installed（deactivated_at 記録）、新対象 → active（activated_at 記録）
```

worker は `current` symlink 越しに `bin/yt-dlp --version` を読むだけで、
上記のいずれにも関与しない（§2.4）。

### 4.3 yt-dlp オプション合成

```
setting の download.*（L2） ─┐
setting の defaults.<kind>.*（L3）
Profile 構造化値（L4）       ├─ None を継承として最終値を1つに解決
一時上書き（L6）             ┘
          ↓ FIELD_TO_ARGS で引数化
Profile.ytdlp_args（L4）→ Playlist.ytdlp_args（L5）→ 一時自由入力（L6）を層順連結
          ↓ 予約引数ガード・警告収集
アプリ予約引数（L1）を最後に注入 → 単一 source_url
```

- 構造化値は最終値だけを出力し、勝った層・由来・フィールド名を `ArgumentOrigin` に保持する
- 自由文字列は `shlex.split` 後も元のトークン順を維持し、同一オプションは後段の層を yt-dlp の後勝ちで優先する
- discover はレート制御、Playlist 自由入力、`--flat-playlist` / `--simulate` / 識別情報 print だけを使い、レイアウト引数を含めない
- download は構造化値、ファイル名方針、自由入力の後に、Staging の `--paths`、相対 `--output`、進捗・after_move print を注入する

### 4.4 レイアウトと Staging パスの解決

```
playlist_profile.subpath（{playlist.*} / {profile.*}）
  → 変数展開 → NFC / Windows互換化 → 絶対パス・.. を拒否
  → flat または custom の yt-dlp 出力テンプレートを連結
  → <STAGING_DIR>/<work-id>/<subpath>/<filename>
```

subpath の `{...}` はアプリ独自構文、ファイル名の `%(...)s` は yt-dlp 構文であり、同じ段階では展開しない。Phase 7 の publish は work root からの相対パスをそのまま Storage に移す前提とする。

### 4.5 Storage publish

```
Staging の完成済みファイル
  ├─ 最終相対パスをアダプタ層でも検証（絶対パス / .. を拒否）
  ├─ 最終名の既存確認（既定は上書き拒否）
  ├─ 同一ディレクトリの <dest>.sluicery-tmp-<uuid> へ転送
  ├─ local: 元を保持して hardlink（非対応時 copy）/ remote: rclone copyto
  ├─ local: サイズ + SHA-256 / remote: rclone lsjson --stat のサイズで検証
  ├─ local: renameat2(NO_REPLACE) / remote: moveto --ignore-existing で最終名へ切替
  └─ 最終化成功後に Staging の元ファイルを削除
```

どの失敗段階でも最終名は作らない。残った `.sluicery-tmp-*` は自動削除せず、
`PublishResult.temporary_rel` で報告する。Phase 13 の整合性走査と将来の掃除 CLI が検出対象とする。

### 4.6 Storage 接続テスト

```
疎通 → 認証 → 一覧 → UUID 付きテストファイルの作成・読み出し・削除
```

- local は認証を `not_applicable` とし、成功と区別する
- remote は rclone の分類から、到達不能なら疎通、認証拒否なら認証、対象パス不正なら一覧の失敗へ写像する
- 前段が失敗した段階は `skipped` として4段階すべてを必ず返す
- テストファイルの削除に失敗した場合は `cleanup_warning` と書き込み段階の失敗として返す

### 4.7 Task worker と回収

```
worker 起動
  ├─ DB migration が head になるまで待つ
  ├─ yt-dlp current が ready になるまで待つ（degraded 起動を維持）
  └─ poll（既定3秒 + 0〜1秒 jitter）
       ├─ 起動ごとに service / container / PID / nonce から一意な worker_id を生成
       ├─ claim: pending / queued / 期限切れ blocked のうち
       │    available_at・blocked_until・依存先 succeeded を満たす1件を
       │    UPDATE ... RETURNING で running にし、worker_id / started_at /
       │    heartbeat_at も同じ SQL で記録
       ├─ handler と heartbeat を並行実行
       │    └─ heartbeat 時に cancel_requested を検知して handler.cancel()
       └─ 結果を確定
            ├─ succeeded / unavailable / cancelled: 終端
            ├─ failed: attempts +1、上限未満なら available_at 付き pending
            └─ blocked: attempts は変えず blocked_until 付き blocked

SIGTERM
  ├─ 新規 claim を停止
  ├─ handler.cancel()（外部処理はプロセスグループ終了）
  └─ Task を attempts 不変の pending に戻し、所有情報をクリア
     Staging と中間ファイルには触れない

app stale reaper
  └─ heartbeat が既定180秒より古い running を attempts +1 で pending へ回収
     （max_attempts 到達時は unavailable）。閾値未満は更新しない
```

依存元が `failed` / `unavailable` で終端した時点で、`TaskRepository` が後続チェーンを
`cancelled` へ伝播する。claim クエリには「依存先が `succeeded`」の条件だけを持たせ、
失敗伝播の再帰処理を混ぜない。

進捗は `payload_json.progress` に単一 UPDATE で保存する。更新は所有中の `worker_id` と
`running` を条件にするため、stale 回収済みの旧 worker は新しい所有者の進捗を上書きできない。
成功・失敗・blocked・shutdownの実行結果確定も同じ所有権条件を持つ単一UPDATEとし、stale回収後の
旧workerによる状態上書きを拒否する。cancel / retryは対象状態を条件にした単一UPDATEでclaimとの
競合を直列化し、最後のheartbeat後のcancel要求はfailed / blockedより優先してcancelledへ確定する。

### 4.8 Targetパイプラインの投入とpayload受け渡し

```
download(network) → verify(compute) → postprocess(compute) → publish(network) → index(network)
```

5 Taskは共通の `work_id` / `target_id` を持ち、チェーン全体を1 transactionで投入する。
ハンドラは `TaskResult.payload_update` で自身の `payload_json` へ必要最小限の結果を統合し、
後段は自身の `depends_on_task_id` から成功済み依存先のpayloadを読む。実行時のTask IDは
workerが永続化対象外の `_execution` として渡す。進捗とハンドラ結果は所有権付きで書き込み、
payloadに資格情報やURLは格納しない。

## 5. 拡張点の実装状況

| 拡張点 | 状態 |
|---|---|
| `LayoutStrategy`（jellyfin / navidrome） | `flat` / `custom` を実装済み。jellyfin / navidrome は未着手 |
| `PostProcessor` | Protocolと空チェーンの素通しTaskを実装済み。実変換アダプタは未実装 |
| `StorageAdapter`（local / remote） | 6メソッドの Protocol と共通結果型、local / remote-rclone を実装済み。remote の実機検証対象は SMB のみ |
| `StorageAdapter`（mount） | 未実装。factory は Phase 19 予定の明示エラーを返し、空実装クラスは置かない |
| イベントフック（Jellyfin/Navidrome スキャン等） | 未着手（`event_log` への記録のみ実装予定） |

## 6. 外部依存（yt-dlp / rclone / ffmpeg）との境界

- yt-dlp: 永続 volume 上の venv に公式 `default` extras 付きでインストール。
  `mutagen`（音声メタデータ・サムネイル埋め込み）等も venv に含め、アプリイメージには焼き込まない
  （要件定義 §5）。導入契約マーカーで旧 venv を検出し、更新時に不足依存を自動修復する
- rclone / ffmpeg: イメージに焼き込む。バージョンは Dockerfile 内で明示固定
- いずれも CLI を subprocess 経由で呼び出す。Python API・shell 経由の呼び出しは行わない
- rclone は `--use-json-log --log-level INFO --ask-password=false` を共通指定し、必要な転送では
  `--stats` を加える。アプリ側 Task リトライとの二重化を避けるため `--retries 1` と
  `--low-level-retries 1` に抑える。設定ファイルは読まず、`--config /dev/null` と
  `RCLONE_CONFIG_<REMOTE>_<KEY>` の子プロセス限定環境変数を使う
- yt-dlp との出力プロトコル（Phase 3）:
  - `--progress-template "download:SLUICERY_PROGRESS %(progress)j"` で進捗を JSON 行として出力させる
  - `--print "[WHEN:]SLUICERY_PRINT %(...)"`（`%()j` で info dict 全体を JSON 化できる）でメタデータ・
    保存パス等を出力させる。`WHEN` は `--use-postprocessor` と同じ値が使える（`after_move` 等）
  - 上記2つの行頭プレフィックスで stdout を demux する（`downloader/protocol.py`）。プレフィックスの
    無い行は無視する
  - ロケールは `LC_ALL=C` に固定（エラー分類が英語メッセージに依存するため）
  - 子プロセスは新しいプロセスグループで起動し、タイムアウト・キャンセル時はグループ単位で終了させる
    （yt-dlp が子プロセスとして起動する ffmpeg が孤児化しないようにする）
  - 実機（yt-dlp 2026.07.04）で上記テンプレート構文の出力を確認済み
- ファイル名境界（Phase 4、yt-dlp 2026.07.04 で実測）:
  - `--windows-filenames` は `\ / : * ? " < > |` を削除せず、見た目の近い Unicode 文字
    （`⧹ ⧸ ： ＊ ？ ＂ ＜ ＞ ｜`）へ置換した。日本語と絵文字は保持された
  - Windows 予約語そのもの（`CON.mov`）と、拡張子直前のタイトル由来のドット・空白
    （`末尾. .mov`）は残った。ただし sluicery の標準テンプレートは末尾に `[<source_id>]`
    を必須とするため、生成される完全な stem が `CON` 等になることはない
  - `--trim-filenames` はテンプレート末尾の ID まで切り詰めうるため、flat のタイトル部分を
    120 byte に制限した上で使用する。ユーザー入力のディレクトリ要素は `core/naming.py` が
    予約語・禁止文字・末尾ドット/空白を処理する（D-018）

## 7. 設計判断の記録

### D-001: 権限降格に gosu ではなく setpriv（util-linux）を使う

- 日付: 2026-08-08
- 背景: PUID/PGID/UMASK を実行時に反映するには、root で起動してからアプリユーザーに降格する必要がある（要件定義 N-5）
- 選択肢: (a) gosu を GitHub リリースから取得して固定 (b) su-exec（Alpine 系、Debian には無い） (c) util-linux 同梱の setpriv
- 決定: (c)。Debian slim イメージに標準で入っており、追加の外部バイナリ取得・checksum 管理が不要
- 影響: なし

### D-002: ffmpeg は静的ビルドを checksum 検証して導入する

- 日付: 2026-08-08
- 背景: 要件定義 §4.2 で rclone / ffmpeg のバージョンを Dockerfile 内で明示固定することが求められている。apt 経由だと Debian リポジトリの状態に依存し、後から同じバージョンを再現できない
- 選択肢: (a) apt-get install ffmpeg （バージョン追跡が困難） (b) johnvansickle.com の静的ビルドを sha256 固定して取得
- 決定: (b)。取得 URL 自体は「最新の release」を指す固定文字列だが、ビルド時に sha256 を検証するため、上流が更新されればビルドが失敗して気づける（無言で異なるバイナリが混入しない）
- 影響: バージョンを上げる際は `FFMPEG_SHA256` を手動で更新する必要がある
- 補強（2026-08-08）: 取得 URL を `ARG FFMPEG_URL` として build-arg 化した。johnvansickle は最新版を固定名で配布し、旧版はバージョン番号付きファイル名で `old-releases/` 配下に残し続けるため、上流ローテーションで checksum 不一致が発生した場合は `old-releases/` の versioned URL に `FFMPEG_URL` を差し替えるだけで、以前と同一バージョンを再取得できる（イメージの再現性が壊れない）

### D-003: requirements.lock はこのセッションでは生成できていない

- 日付: 2026-08-08
- 背景: `pip-compile --generate-hashes` の実行には pip または Docker デーモンが必要だが、実装セッションの実行環境にはどちらも無かった（pip 未インストール、Docker Desktop の WSL 連携が無効）
- 決定: ハッシュを手で捏造しない。`make lock` ターゲット（Docker + ネットワークがある環境で pip-compile を実行）を用意し、ユーザー側での実行を前提とする
- 影響: `requirements.lock` が生成されるまで `docker compose up` は失敗する。AISTATE.md の未解決 #1 を参照
- 追記（2026-08-08、Phase 2 前半）: 本セッションでも docker デーモンへの権限がなく（socket が root:docker 所有でユーザー未所属）、`make lock` を実行できていない。ユーザー側で `sudo usermod -aG docker $USER` 後、`make lock` → `docker compose up -d --build` の実行を依頼した
- 解決（2026-08-08、Phase 2 後半）: ユーザーが docker グループへの追加を完了。`requirements.lock` を生成し、`docker compose up -d --build` で app / worker-network / worker-compute の起動を確認した（詳細は変更履歴.md、D-010 参照）

### D-004: `SECRET_KEY` はローテーション非対応とする

- 日付: 2026-08-08
- 背景: `storage.credentials_encrypted` を Fernet で暗号化する以上、鍵が変わると復号できなくなる。再暗号化コマンドを実装する選択肢もあった
- 選択肢: (a) 再暗号化コマンドを実装し、旧鍵→新鍵の移行を自動化する (b) ローテーション非対応とし、紛失・変更時はクレデンシャル再入力を促す
- 決定: (b)。Phase 2 の時点では Storage 数も少なく、再暗号化の実装・テストコストに見合わない。鍵指紋（`setting` テーブルに sha256 ハッシュを保存）を照合し、意図しない鍵変更を検知して明確な警告を出すことで、原因不明の復号エラーだけは防ぐ
- 影響: 鍵を変更する運用は、各 Storage の認証情報を手動で再入力する前提になる。README.md / docs/legal.md に明記

### D-005: 運用パラメータを `.env` から `setting` テーブルへ移す

- 日付: 2026-08-08
- 背景: 要件定義 §17 は `STAGING_WARN_PCT` 等を `.env` の一覧に含めていたが、これらは Web UI からの変更が要件で想定されている運用パラメータであり、`.env` 編集＋再起動でしか変更できないのは要件（Web UI からの設定変更）と矛盾する
- 選択肢: (a) 要件定義 §17 の通り `.env` に置く (b) `.env` はインフラ・セキュリティ境界に限定し、運用パラメータは DB の `setting` テーブルに移す
- 決定: (b)。既定値はコード側（`core/settings.py` の `CODE_DEFAULTS`）に定義し、`setting` テーブルにはユーザーが明示的に上書きした項目のみを保存する二層構造とした
- 影響: 要件定義 §17 の環境変数一覧との差分が生じる（本書 §3 参照）。`.env.example` から該当項目を削除した

### D-006: `Task.claim_next()` は単一 UPDATE ... RETURNING でアトミックに実装する

- 日付: 2026-08-08
- 背景: 複数ワーカー（プロセス）が同一 Task を同時に claim してはならない（要件 §8.3）
- 選択肢: (a) `BEGIN IMMEDIATE` で明示的に排他ロックを取ってから SELECT→UPDATE の2文で実装する (b) 候補選定（`WHERE status=queued ORDER BY priority DESC, id ASC LIMIT 1`）と `queued→running` への更新を単一の `UPDATE ... WHERE id IN (...) ... RETURNING` 文にまとめる
- 決定: (b)。PRAGMA で `journal_mode=WAL` と `busy_timeout=5000` を設定済みであり、SQLite は書き込みを直列化するため、単一 UPDATE 文自体がアトミックな排他になる。実装がシンプルで、明示的なロック管理（例外時の unlock 漏れ等）のリスクがない
- 影響: 20〜30スレッドが同一/複数 Task を奪い合う並行テストで二重 claim が発生しないことを確認済み（`tests/test_task_claim_next.py`）

### D-007: DB のタイムスタンプに独自の `UTCDateTime` 型を使う

- 日付: 2026-08-08
- 背景: SQLAlchemy の `DateTime(timezone=True)` は SQLite では tzinfo を保持しない（書き込み時に無言で破棄、読み出し時は naive datetime）。テスト作成中に発覚した
- 選択肢: (a) アプリ側が読み出し後に毎回 `.replace(tzinfo=UTC)` するルールを徹底する (b) `TypeDecorator` でカラム型自体に UTC の付け外しを組み込む
- 決定: (b)。(a) は徹底を人手に頼ることになり、忘れた箇所だけ naive datetime が混入する事故が起きやすい。カラム型に閉じ込めることで、モデル層を使う限り自動的に守られる
- 影響: 書き込み時に naive datetime を渡すと `ValueError` になる（`datetime.now(UTC)` 等、必ず aware で渡す必要がある）

### D-008: Alembic autogenerate は SQLite 上の CHECK 制約を正しく比較できない（既知の制限）

- 日付: 2026-08-08
- 背景: `alembic revision --autogenerate` や `alembic check` を、生成直後の DB に対して実行しても、Enum 由来の CHECK 制約が「削除→再作成」の差分として毎回検出される
- 原因: SQLAlchemy は SQLite の CHECK 制約をリレクションで完全には復元できず、比較対象を構造的に一致させられない（SQLAlchemy/Alembic 側の既知の制限であり、本プロジェクトの実装ミスではない）
- 対応: 実害はない（`upgrade` / `downgrade` 自体は正しく動作する。§9.2 で確認済み）。今後 Phase 3 以降で `alembic revision --autogenerate` を実行する際、生成物に CHECK 制約の削除/再作成が混ざっていたら、実際の変更に無関係なら手で取り除いてからコミットすること（§5.2 の「手で確認・整形」の一環）

### D-009: `user` の2件目禁止はリポジトリ層で担保する

- 日付: 2026-08-08
- 背景: 要件定義は「2件目のユーザー作成を禁止」とだけ規定しており、DB 制約かアプリ層かの選択は実装時判断とされていた（§4.3）
- 選択肢: (a) SQLite の `CHECK` やトリガーでテーブル全体を1行に制限する (b) `UserRepository.create_single()` で作成前に既存行の有無を確認する
- 決定: (b)。SQLite で「テーブル全体で高々1行」を宣言的な制約だけで表現するのは技巧的（トリガーが必要）になり、Phase 2 のリポジトリ層の「呼び出し側が固まっていないものは作らない」方針とも整合しないため、アプリ層のガードで十分と判断した
- 影響: `UserRepository.create_single()` を経由しない生の `session.add(User(...))` では防げない。呼び出し側は必ずリポジトリ経由でユーザーを作成すること

### D-010: `MEDIA_ROOT` の書き込み検証は環境変数の値ではなく固定パスに対して行う

- 日付: 2026-08-08
- 背景: `docker compose up -d --build` による実地検証で発覚。`MEDIA_ROOT` はホスト側の bind mount ソースパスであり、`compose.yaml` は常に `${MEDIA_ROOT}:/mnt/media` でマウントする。コンテナ内から見える実際のパスは常に `/mnt/media` で、`MEDIA_ROOT` の値そのもの（例: `/tmp/foo`）はコンテナ内には存在しない。`config.py` の `Settings` が `MEDIA_ROOT` フィールドの値をそのまま存在・書き込みチェックしていたため、既定値（`/mnt/media`）以外を設定すると起動できなかった
- 選択肢: (a) `MEDIA_ROOT` フィールドの検証をやめる（entrypoint.sh の事前チェックのみに委ねる） (b) 検証対象を固定のクラス定数 `MEDIA_MOUNT_PATH`（`/mnt/media`）に切り替え、`MEDIA_ROOT` フィールド自体は表示・記録用として残す
- 決定: (b)。`sluicery config check` で書き込み可否を可視化する要件（docs/phase2_指示書.md §2.2）は維持しつつ、実際に意味のあるパスを検証する

### D-014: 未知の yt-dlp エラーメッセージは `failed`（安全側）に分類する

- 決定: (c)。`unavailable` に誤って倒すと自動リトライ対象から外れて放置される。`blocked` に誤って倒すとリトライ回数の上限がいつまでも効かなくなる。`failed` はリトライ回数を消費しつつ既定の上限（`retry.max_attempts`）で最終的に `unavailable` へ落ちるため、誤分類時の実害が一番小さい

- 決定: (b)。blocked は attempts を消費せず、blocked_until 経過後に自然に再claimする。回復不能と試行上限到達を明示する unavailable も追加する
- 影響: D-028 と未解決 #2 を解消。未知の一時失敗は failed として上限まで再試行し、その後 unavailable になる

### D-030: compose の全サービスで `init: true` を使う

- 日付: 2026-08-12
- 背景: worker が外部プロセスとその子を継続的に起動するため、PID 1 が孤児化した孫プロセスを reap できない構成は長期運用で zombie を蓄積しうる
- 選択肢: (a) アプリだけで reap を実装 (b) Docker Compose の init を使う
- 決定: (b)。app / worker-network / worker-compute の全サービスへ `init: true` を設定する
- 影響: 未解決 #3 を解消。コンテナ内 PID 1 は tini 相当になるが、ホスト上の volume・bind mount・ネットワークは増えない

### D-031: graceful shutdown は Task を `pending` に戻し Staging を保持する

- 日付: 2026-08-12
- 背景: download は最長6時間で、SIGTERM 後に完了を待つ運用はできない。一方、中間ファイルを消すと再起動のたびに取得がゼロからになる
- 選択肢: (a) 完了まで待つ (b) failed にする (c) attempts 不変の pending に戻す
- 決定: (c)。新規 claim を止め、handler をキャンセルし、所有情報と cancel_requested をクリアして即時再実行可能にする
- 影響: compose の stop_grace_period は30秒、worker.shutdown_grace_sec は20秒。Staging の削除 API は呼ばず、Phase 7 の yt-dlp `--continue` で再開できる

### D-032: `available_at` と `blocked_until` を分離する

- 日付: 2026-08-12
- 背景: 自身の一時失敗と外的要因の待機を同じ時刻にすると、attempts を消費すべきか判定できない
- 選択肢: (a) 単一の retry_at (b) 原因別の2列
- 決定: (b)。failed は attempts +1 と available_at、blocked は attempts 不変と blocked_until を使う
- 影響: claim は両時刻を満たした pending / queued と、期限切れ blocked を対象にする

### D-033: Task進捗は `payload_json.progress` に保存する

- 選択肢: (a) 専用列 (b) payload_json の一部
- 決定: (b)。2秒または5%のいずれかを満たすときだけ単一 UPDATE し、最終結果は必ず書く
- 影響: 更新条件へ worker所有権を含め、stale回収後の旧workerによる上書きを防ぐ。Phase 11で必要なら専用列化を再評価する

### D-034: 依存失敗のキャンセルは失敗確定時に伝播する

- 日付: 2026-08-12
- 背景: claim クエリに依存成功の確認と失敗チェーンの更新を同時に持たせると、アトミック claim が複雑になる
- 選択肢: (a) claim 時に失敗した依存を探索 (b) failed / unavailable 確定時に後続を再帰キャンセル
- 決定: (b)。claim は依存先 succeeded の存在確認だけを行い、終端失敗メソッドが未実行の後続を cancelled にする
- 影響: Phase 7 の download → verify → postprocess → publish → index チェーンを単純な依存列で実装できる

### D-035: 検証用Taskは運用設定で明示的に有効化する

- 日付: 2026-08-12

- 選択肢: (a) 常時登録 (b) worker.enable_test_tasks を既定 false とする

### D-036: ffmpeg 7.0.2-staticはverifyに使用し、区間取得の制限を残す

- 日付: 2026-08-12
- 背景: `--download-sections` の1秒区間取得で ffmpeg が `-11`（SIGSEGV）終了しており、Phase 7 の verify に同じ静的ビルドを使えるか再評価が必要だった
- 選択肢: (a) ffmpeg / ffprobe 静的ビルドを全面的に差し替える (b) verify の ffprobe 経路が健全なら現行ビルドを維持する
- 決定: (b)。`ffmpeg -version` / `ffprobe -version` は正常終了し、既存の `trailer_1080p.mov`を `ffprobe -v error -show_format -show_streams -of json` で解析して2 streamと32.995秒のdurationを取得できた。同一素材の `--download-sections "*0-1" --force-keyframes-at-cuts` では `ffmpeg exited with code -11` を再現したため、障害は区間切り出し経路に局在すると判定した
- 影響: Phase 7 verify は現行 ffprobe で実装する。区間取得は現バージョンの既知の制限とし、パイプラインの判定・変換機能には使用しない

### D-037: yt-dlp分類をTaskとTargetの異なる状態軸へ写像する

- 日付: 2026-08-12
- 背景: Taskは1回の実行状態、Targetはコンテンツの永続状態であり、同じ `unavailable` でも意味が異なる
- 決定:

  | yt-dlp分類 | Task | Target |
  |---|---|---|
  | `ok` | `succeeded` | チェーン継続中は `downloading` |
  | `failed` | `failed`（上限まで再試行） | `failed`、`retry_count` を増やす |
  | `unavailable` | `unavailable` | `unavailable` |
  | `blocked` | `blocked`（attempts不変） | `blocked`（retry_count不変） |

- 影響: Target更新は現在状態を条件に含む単一UPDATEとし、後続TaskはTask依存失敗伝播に任せる。エラー時もStagingのファイルは削除しない

### D-038: verifyのdurationは記録だけ行い異常判定に使わない

- 日付: 2026-08-12
- 背景: discover値とffprobe値の比較は破損検知に見えるが、generic extractorの欠損、ライブ、可変長メディアで誤検知しうる
- 決定: ffprobeの `duration` は秒数でpayload / Artifactへ記録するが、Phase 7では成否判定に使用しない。非0 byteとffprobeの正常終了・JSON解析可能性を健全性判定とする
- 影響: duration差分の判定はPhase 13の整合性チェックで再検討する。verify失敗時は理由をpayloadへ残し、Stagingを削除しない
