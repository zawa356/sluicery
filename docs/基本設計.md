# sluicery 基本設計

本書は「どう作るか（HOW）」を記録する。仕様の根拠（WHAT）は `docs/要件定義.md` を参照。
実装に合わせて随時更新する。

## 1. 全体構成図（サービス／データフロー）

```
                 ┌────────────────────┐
                 │   Web ブラウザ       │
                 └─────────┬──────────┘
                            │ HTTP
                 ┌─────────▼──────────┐        ┌───────────────┐
                 │  app                │        │  永続 volume   │
                 │  - FastAPI          │◄──────►│  /data         │
                 │  - Jinja2 + HTMX    │        │  - sqlite db   │
                 │  - APScheduler      │        │  - ytdlp-venv  │
                 └─────────┬──────────┘        │  - logs        │
                            │ Task 投入（DB経由）  └───────┬───────┘
        ┌───────────────────┴───────────────────┐         │
        │                                        │         │
┌───────▼─────────┐                    ┌─────────▼───────┐ │
│ worker-network   │                    │ worker-compute   │ │
│ discover/download│                    │ postprocess/verify│ │
│ /publish         │                    │ （現バージョンでは│ │
│ 並行度 既定 1     │                    │  実質待機）       │ │
└───────┬─────────┘                    └─────────┬────────┘ │
        │                                          │         │
        │  yt-dlp subprocess                       │ ffmpeg  │
        ▼                                          ▼         │
   ソース動画/音楽サイト                    /data/staging（bind/volume）
        │                                          │
        └──────────────► Storage アダプタ ◄────────┘

                            │
                            ▼
                  最終保存先（ホスト bind mount、rclone、
                  または明示的privileged kernel mount）
```

3 サービス（app / worker-network / worker-compute）は同一イメージを使い、起動コマンドで役割を分ける（要件定義 §3.1）。

## 3. データモデル（実装スキーマと要件定義の論理設計との差分）

Phase 2 で要件定義 §7.1 の全12テーブルを実装した。論理設計との差分は以下の通り。

| 項目 | 差分 | 理由 |
|---|---|---|
| `TaskStatus` | `pending` / `queued` / `running` / `succeeded` / `failed` / `unavailable` / `blocked` / `cancelled` | Phase 6 で外的要因を試行回数を消費せず保留する `blocked` と、回復不能・試行上限到達を表す `unavailable` を追加（D-029） |
| `RunStatus`（新規） | `running` / `succeeded` / `failed` / `cancelled` / `skipped` | `run.status` カラムに要件定義が値を与えていなかったため新設。`TaskStatus` と異なり `pending`/`queued` は持たない。`skipped`は時間帯外または同一Playlistの同期中に自動実行を安全に見送った監査記録に使う |
| `task.created_at` | 追加（`updated_at` は追加せず） | 要件定義の論理設計にはないが、`claim_next()` の候補選定で `priority` 降順・`id` 昇順の同点タイブレークに ID の単調増加性を利用しており、実質的に FIFO を保証している。将来的に別途生成時刻が必要になった場合の保険としても追加 |
| `task.available_at` / `blocked_until` | nullable UTC datetime を追加 | 自身の一時失敗によるバックオフと外的要因による保留を区別する（D-032） |
| `task.blocked_reason` | nullable 文字列を追加 | Storage 等の外的要因の分類・理由を保持する |
| `task.heartbeat_at` / `worker_id` | nullable UTC datetime / 文字列を追加 | 実行所有者を明示し、応答不能 worker の stale Task を安全に回収する |
| `task.cancel_requested` | NOT NULL bool（既定 false）を追加 | CLI / 将来の UI から実行中 handler へ非同期キャンセルを伝える |
| `setting` の主キー | `key`（文字列）を主キーとし、`id` 列を持たない | 要件定義の論理設計自体が `key, value_json, updated_at` のみで `id` を持たない自然キー設計だったため、そのまま踏襲した。§4.6「主キーは整数 autoincrement」の原則の唯一の例外 |
| `user` の2件目禁止 | DB 制約ではなく `UserRepository.create_single()`（リポジトリ層）で担保 | `username` の `UNIQUE` 制約だけでは異なるユーザー名の2件目を防げない。SQLite で「テーブル全体で1行のみ」を宣言的に強制する簡潔な方法がないため、アプリ層でチェックする方式にした |
| タイムスタンプ型 | `DateTime(timezone=True)` ではなく独自の `UTCDateTime`（`TypeDecorator`） | SQLAlchemy + SQLite では `DateTime(timezone=True)` を指定しても tzinfo が書き込み時に無言で破棄され、読み出し時も naive datetime になる（テストで実際に発覚）。`UTCDateTime` は書き込み時に tz aware であることを検証して UTC に変換・保存し、読み出し時に `tzinfo=UTC` を明示的に付与することで §3.3 の方針を実際に満たす |
| `.env` → DB へ移した項目 | `download.*` / `schedule.*` / `ytdlp.*` / `storage.*` に加え、Phase 6 の `worker.*`（poll、heartbeat、stale、retry、progress、shutdown、検証用 Task の有効化）を `setting` テーブル側の運用パラメータとして定義 | `.env` はセキュリティ境界とインフラ設定に限定する D-005 に従った |
| `ytdlp_release`（新規テーブル、Phase 3） | `id, version, installed_at, source(initial/manual/auto), status(installed/active/removed), activated_at, deactivated_at, smoketest_result_json, notes, created_at, updated_at` | 要件定義 §5.3 の「更新履歴（バージョン、日時、結果）を DB に記録する」に対応するテーブルが論理設計に無かったため新設（D-011） |
| `profile` の設定フラグ | `audio_extract` / `embed_metadata` / `embed_thumbnail` / `embed_chapters` / `subtitle_auto` / `subtitle_embed` を nullable に変更 | 要件定義 §7.1 は三状態を明示していないが、オプション合成で「未設定（継承）」と明示的な `false` を区別するため（D-017） |
| `playlist.missing_policy` | `leave` / `redownload` / `ignore`（既定`leave`）を追加 | 要件定義 §11.3のPlaylist単位の選択を永続化する列が論理設計に無かったため追加 |
| `artifact.manual_link_previous_path` / `manual_linked_at` | 取消可能な手動リンク履歴を追加 | 手動リンクはDBパスだけを更新するため、元の記録パスを保持して取消可能にする |
| `artifact` の冪等キー | `UNIQUE(target_id, role, storage_id, relative_path)` を追加 | index成功直後のworker停止による再実行で同一Artifactを重複作成しないため |

## 4. 主要なフローのシーケンス（同期・パイプライン・relink）

### 4.0 認証とセッション

```
初回起動 ─ UserRepository.create_single() ─ argon2ハッシュだけをDBへ保存

未認証アクセス ─ ランダムな匿名セッションIDを発行
  ├─ Cookie: HKDFで用途分離した鍵 + itsdangerousで署名
  └─ DB: セッションIDのSHA-256だけをauth_sessionへ保存（固定30日期限）

ログイン成功 ─ 旧匿名セッションを削除 ─ 新しい認証済みセッションを発行
パスワード変更 ─ 現在のパスワードを検証 ─ 全セッションを削除 ─ 再ログイン
```

認証不要なのは `/healthz`、`/login`、`/static/*` だけで、それ以外はミドルウェアが既定で
認証を要求する。失敗回数とロック期限は `user` テーブルへ保存し、既定5回・15分のロックを
プロセス再起動後も維持する。ロック中は正しいパスワードも拒否し、応答文はユーザー名の
存在有無にかかわらず統一する。

CSRFトークンは別のHKDF用途で導出した鍵を使い、セッションIDのHMAC-SHA256として発行する。
FastAPIの全ルート共通依存がGET以外を検証するため、個別ルートで保護を
付け忘れない。通常フォームはhidden input、HTMXは`X-CSRF-Token`ヘッダーで渡す。

Web UIはJinja2の共通テンプレートを使い、7グループのナビゲーション、DBセッションに一度だけ
保存するフラッシュメッセージ、403 / 404 / 500の専用ページを提供する。CSSとHTMX 2.0.10は
`web/static`へ同梱し、実行時にCDNへ接続しない。

### 4.1 yt-dlp venv のインストール（`downloader/version.install()`）

```
app (CLI/自動導入スレッド)
  │
  ├─ fcntl.flock(.lock) を取得（app のみ書き込み。worker は読み取り専用）
  ├─ [--version 指定 かつ --force 無し かつ 導入済み] なら
  │    └─ 現在 not_installed/broken なら active 化して早期リターン
  │       それ以外はそのまま早期リターン（何もしない）
  ├─ versions/.tmp-<uuid>/ に python -m venv
  ├─ pip install "yt-dlp[default]"（バージョン指定時は "yt-dlp[default]==<version>"）
  ├─ venv に導入契約マーカー（yt-dlp-default-extras-v1）を記録
  ├─ bin/yt-dlp --version で実際の導入バージョンを確認
  ├─ versions/<version>/ にリネーム（同名が既に有れば .tmp を破棄し既存を採用）
  ├─ ytdlp_release レコードを作成/更新
  └─ [current が無かった場合のみ] current を新バージョンに切替え、
       DB 上の active を1件に保つ（旧 active があれば installed に戻す）

失敗時: .tmp を確実に削除し、current・DB は一切変更しない
```

`get_status()` は実行ファイルだけでなく導入契約マーカーも確認する。Phase 3 までの本体のみの
venv や将来の契約変更は `broken` と判定し、自動導入が同一バージョンでも venv を再構築する。

### 4.2 バージョン切替（`downloader/version.use()`）

```
app
  ├─ fcntl.flock(.lock)
  ├─ 対象バージョンの導入確認（未導入なら UnknownVersionError）
  ├─ os.symlink(target, tmp_link) → tmp_link.replace(current)（原子的差替え）
  └─ DB: 旧 active → installed（deactivated_at 記録）、新対象 → active（activated_at 記録）
```

worker は `current` symlink 越しに `bin/yt-dlp --version` を読むだけで、
上記のいずれにも関与しない（§2.4）。

### 4.3 yt-dlp オプション合成

```
setting の download.*（L2） ─┐
setting の defaults.<kind>.*（L3）
Profile 構造化値（L4）       ├─ None を継承として最終値を1つに解決
一時上書き（L6）             ┘
          ↓ FIELD_TO_ARGS で引数化
Profile.ytdlp_args（L4）→ Playlist.ytdlp_args（L5）→ 一時自由入力（L6）を層順連結
          ↓ 予約引数ガード・警告収集
アプリ予約引数（L1）を最後に注入 → 単一 source_url
```

- 構造化値は最終値だけを出力し、勝った層・由来・フィールド名を `ArgumentOrigin` に保持する
- 自由文字列は `shlex.split` 後も元のトークン順を維持し、同一オプションは後段の層を yt-dlp の後勝ちで優先する
- discover はレート制御、Playlist 自由入力、`--flat-playlist` / `--simulate` / 識別情報 print だけを使い、レイアウト引数を含めない
- download は構造化値、ファイル名方針、自由入力の後に、Staging の `--paths`、相対 `--output`、進捗・after_move print を注入する

### 4.4 レイアウトと Staging パスの解決

```
playlist_profile.subpath（{playlist.*} / {profile.*}）
  → 変数展開 → NFC / Windows互換化 → 絶対パス・.. を拒否
  → flat または custom の yt-dlp 出力テンプレートを連結
  → <STAGING_DIR>/<work-id>/<subpath>/<filename>
```

subpath の `{...}` はアプリ独自構文、ファイル名の `%(...)s` は yt-dlp 構文であり、同じ段階では展開しない。Phase 7 の publish は work root からの相対パスをそのまま Storage に移す前提とする。

### 4.5 Storage publish

```
Staging の完成済みファイル
  ├─ 最終相対パスをアダプタ層でも検証（絶対パス / .. を拒否）
  ├─ 最終名の既存確認（既定は上書き拒否）
  ├─ 同一ディレクトリの <dest>.sluicery-tmp-<uuid> へ転送
  ├─ local: 元を保持して hardlink（非対応時 copy）/ remote: rclone copyto
  ├─ local: サイズ + SHA-256 / remote: rclone lsjson --stat のサイズで検証
  ├─ local: renameat2(NO_REPLACE) / remote: moveto --ignore-existing で最終名へ切替
  └─ 最終化成功後も Staging の元ファイルを保持（index後に削除）
```

どの失敗段階でも最終名は作らない。残った `.sluicery-tmp-*` は自動削除せず、
`PublishResult.temporary_rel` で報告する。Phase 13 の整合性走査と将来の掃除 CLI が検出対象とする。

### 4.6 Storage 接続テスト

```
疎通 → 認証 → 一覧 → UUID 付きテストファイルの作成・読み出し・削除
```

- local は認証を `not_applicable` とし、成功と区別する
- remote は rclone の分類から、到達不能なら疎通、認証拒否なら認証、対象パス不正なら一覧の失敗へ写像する
- 前段が失敗した段階は `skipped` として4段階すべてを必ず返す
- テストファイルの削除に失敗した場合は `cleanup_warning` と書き込み段階の失敗として返す

### 4.7 Task worker と回収

```
worker 起動
  ├─ DB migration が head になるまで待つ
  ├─ yt-dlp current が ready になるまで待つ（degraded 起動を維持）
  └─ poll（既定3秒 + 0〜1秒 jitter）
       ├─ 起動ごとに service / container / PID / nonce から一意な worker_id を生成
       ├─ claim: pending / queued / 期限切れ blocked のうち
       │    available_at・blocked_until・依存先 succeeded を満たす1件を
       │    UPDATE ... RETURNING で running にし、worker_id / started_at /
       │    heartbeat_at も同じ SQL で記録
       ├─ handler と heartbeat を並行実行
       │    └─ heartbeat 時に cancel_requested を検知して handler.cancel()
       └─ 結果を確定
            ├─ succeeded / unavailable / cancelled: 終端
            ├─ failed: attempts +1、上限未満なら available_at 付き pending
            └─ blocked: attempts は変えず blocked_until 付き blocked

SIGTERM
  ├─ 新規 claim を停止
  ├─ handler.cancel()（外部処理はプロセスグループ終了）
  └─ Task を attempts 不変の pending に戻し、所有情報をクリア
     Staging と中間ファイルには触れない

app stale reaper
  └─ heartbeat が既定180秒より古い running を attempts +1 で pending へ回収
     （max_attempts 到達時は unavailable）。閾値未満は更新しない
```

依存元が `failed` / `unavailable` で終端した時点で、`TaskRepository` が後続チェーンを
`cancelled` へ伝播する。claim クエリには「依存先が `succeeded`」の条件だけを持たせ、
失敗伝播の再帰処理を混ぜない。

進捗は `payload_json.progress` に単一 UPDATE で保存する。更新は所有中の `worker_id` と
`running` を条件にするため、stale 回収済みの旧 worker は新しい所有者の進捗を上書きできない。
成功・失敗・blocked・shutdownの実行結果確定も同じ所有権条件を持つ単一UPDATEとし、stale回収後の
旧workerによる状態上書きを拒否する。cancel / retryは対象状態を条件にした単一UPDATEでclaimとの
競合を直列化し、最後のheartbeat後のcancel要求はfailed / blockedより優先してcancelledへ確定する。

### 4.8 Targetパイプラインの投入とpayload受け渡し

```
download(network) → verify(compute) → postprocess(compute) → publish(network) → index(network)
```

5 Taskは共通の `work_id` / `target_id` を持ち、チェーン全体を1 transactionで投入する。
ハンドラは `TaskResult.payload_update` で自身の `payload_json` へ必要最小限の結果を統合し、
後段は自身の `depends_on_task_id` から成功済み依存先のpayloadを読む。実行時のTask IDは
workerが永続化対象外の `_execution` として渡す。進捗とハンドラ結果は所有権付きで書き込み、
payloadに資格情報やURLは格納しない。

### 4.9 Playlistの二相同期

```
CLI / scheduler
  │
  ├─ discover Run + discover(network) Taskを作成
  │    ├─ flat-playlistの結果が空またはエラー
  │    │    └─ Item / Target / last_discover_atを変更せず、empty_resultを記録
  │    └─ 非空の結果
  │         ├─ Item upsert、再登場 active、未出現 activeをdelisted
  │         └─ 新規Item × 有効PlaylistProfileのTargetを作成
  │
  └─ download Run
       ├─ active Itemのpending / 再試行可能failed / blockedを並べる
       ├─ Storageごとに到達性・書込み・容量を1回事前確認
       ├─ 使用不能はTarget blocked、Task未作成
       ├─ 回復済みblocked / failedをpendingへ戻す
       └─ playlist_index順に最大50 Targetの5段チェーンを投入しRunを確定
```

`sync run --all`は、network workerのFIFOで先頭Playlistのdownloadが後続discoverを遅延させないよう、
全Playlistのdiscover完了後に全downloadフェーズを開始する。download Runはチェーンの
実行完了ではなく投入完了時点で確定し、個々の結果はTarget / Taskで追跡する。

### 4.10 Playlist Cookieの展開と削除

```
UIでNetscape形式を検証
  → Playlist.cookies_encryptedへEncryptedJSONで保存（既定無効・write-only）
  → discover / download開始時、有効なPlaylistだけを処理
      → /run/sluicery/cookies-<UUID>.txt を排他的に600で作成
      → --cookies <一時パス> をURLの手前へ注入
      → パス・Cookie値をRunnerのマスク対象に追加
      → 成否・例外にかかわらずfinallyでunlink
```

Composeの全サービスは`/run/sluicery`をtmpfsとしてマウントする。yt-dlpが一時ファイルへ
書き戻してもDBには反映せず、実行終了時に破棄する。`--cookies`の自由入力と
`--cookies-from-browser`は予約引数として拒否し、管理されたPlaylist設定だけを利用する。

### 4.11 Runの監視・ログ・キャンセル

```
Run詳細 ─ Task.payload_json.progress ─ 3秒HTMXポーリング
  │                                      └─ running Taskが0件なら停止
  ├─ DBのrun.log_path ─ strict resolve ─ DATA_DIR内の通常ファイルだけ許可
  │    ├─ 画面: 二次マスク後の末尾N行
  │    └─ download: 二次マスクしながら行単位ストリーミング
  └─ cancel POST ─ queued / waitingは即時cancelled
                    runningはcancel_requestedをheartbeatが検知して協調停止
```

外部CLIのログはRunnerで一次マスクした後、workerがRun単位ファイルへ行単位で集約する。
集約時にも二次マスクし、Taskの`log_excerpt`は末尾4000文字に制限する。URLやフォーム入力を
ログパスの構築へ使わず、境界外、存在しないパス、通常ファイル以外は404として扱う。

download Runは5段チェーンの完了ではなく投入結果を表すため、Run統計と実際のTask状態を
別欄で表示する。Runキャンセル後は、遅れて戻ったhandlerがRunを成功へ上書きできない。

### 4.12 スケジュールの解決と実行

```
app起動（schedulerはworkerでは起動しない）
  ├─ APScheduler SQLAlchemyJobStore ─ 既存SQLiteへ永続化
  ├─ 起動時整合 ─ runnable Playlist × {discover, download}
  │    ├─ Playlist個別cron ─ 設定ありなら採用
  │    └─ settingのグローバルcron ─ 個別未設定時のfallback
  ├─ CronTrigger ─ .envのTZで解釈 ─ jobごとに一様な±jitter位相
  ├─ schedule.integrity_cron ─ 全Artifactの日次整合性チェック
  └─ 60秒ごとの整合 ─ 設定変更を反映し、削除・disabled・pausedのjobを除去

発火
  ├─ downloadだけ実行可能時間帯を判定（日中 / 日跨ぎ / 同時刻=終日）
  │    └─ 時間外 ─ Taskを作らずskipped Runを記録
  ├─ SQLite BEGIN IMMEDIATEで同一Playlistの活動中Run/Taskを検査
  │    └─ 手動・自動syncが活動中 ─ Taskを作らずskipped Runを記録
  └─ discover Runまたはdownload Runを既存のcore.sync経路で開始
```

永続jobの引数はPlaylist IDと`discover` / `download`の種別だけとし、URL、Cookie、Storage資格情報を
jobstoreへ複製しない。`coalesce=true`、`max_instances=1`、24時間のmisfire猶予を設定し、停止中の
複数fire timeを復帰時の1回へ畳み込む。設定が変わっていないjobは起動時に置換せず、保存済みの
期限超過`next_run_time`を保持してmisfire判定へ渡す。時刻の表示変換は`SchedulerService.timezone`へ
集約し、ダッシュボードとPlaylist詳細の両方で同じ`TZ`を使う。
整合性jobは引数を持たず、実行時にDBからStorageと運用設定を解決する。
これによりjobstoreへStorageパスや認証情報を複製しない。

起動時にはstale Task回収に加え、活動中Taskを持たない古い`running` Runを終端する。Storage事前確認中の
正当なdownloadと外部CLIを誤回収しないよう、Taskなしdownloadだけは24時間を超えた場合に限定する。
Run回収はschedulerがpausedの起動時だけで、60秒の定期整合では行わない。各jobのtransactionも短く保ち、
Task workerのclaim / heartbeatと同居するSQLite WALへの書込み競合を抑える。

### 4.13 整合性チェックとrelink

```
StorageごとにArtifactのrelative_pathをexistsで確認
  ├─ 全て存在 ─ missing_sinceを解除し、全Artifact復帰済みのTargetをdownloadedへ戻す
  ├─ 不在あり ─ Storage全体を1回だけ再帰走査
  │    ├─ 末尾[source_id]候補が1件 ─ DBのrelative_pathだけを更新
  │    ├─ 0件 ─ missing_sinceとTarget missingを記録
  │    └─ 複数件 ─ 自動選択せずmissingとして手動リンク候補を報告
  └─ exists/走査エラーまたはタイムアウト ─ missing判定を一切行わない
```

再走査候補から別Artifactが追跡中のパスを除外し、同一source IDを持つ別Playlistの実体へ
自動的に付け替えない。整合性境界が呼ぶStorage APIは`exists`と`list_recursive`だけで、
`move`、`publish`、削除操作を持たない。
候補除外用の追跡パスはPlaylist絞り込みと分離し、対象Storageの全Artifactから構築する。
1候補を複数Artifactが要求する場合も所有者を自動決定せず、手動リンク対象とする。

DBから点検スナップショットとAdapterを準備したらread transactionを閉じ、
Storage I/O後に元パス・候補パスの存在を再確認する。その後の短いtransactionで
Artifact / Targetの`updated_at`、Target状態、記録パス、候補の未追跡を再確認し、
走査中のworker完了や別の手動操作があったArtifact / Targetに古い判定を適用しない。
再走査は`integrity.rescan_timeout_sec`をAdapterへ渡し、remoteではRunnerが期限時に
rcloneプロセスを停止する。走査失敗・タイムアウト時は同一Storageの存在確認済みArtifactも
`missing_since`を解除せず、未確認Artifactを残したTargetの誤復帰を防ぐ。

不在確定後はPlaylistの`missing_policy`を適用する。既定の`leave`はTargetを`missing`に保ち、
`redownload`は`pending`、`ignore`は`ignored`へ進める。UI/CLIからの明示操作でも同じ3状態を
選べるが、いずれもArtifactや実ファイルを削除・移動しない。

整合性レポートは選択Storageのmissing TargetとArtifact未追跡ファイルを並べて表示する。
手動リンクでは候補の存在と他Artifactが追跡中でないことを再確認し、DBの
`relative_path`と状態だけを更新する。取消は保存済みの元パスへ戻してmissingにする。
どちらもStorageのファイルを書き換えない。

差分レポートは`membership=delisted`のItemと関連ArtifactのStorage名・記録パスを
読み取り専用で表示する。Playlistと`TZ`のカレンダー日による期間で絞り込めるが、
削除経路は持たせない。retentionとは独立した手動判断用のレポートとする。

### 4.14 フォーマット検査

Profile編集画面から任意のHTTP(S) URLを1件だけ`--simulate --no-playlist`で検査する。
コマンドはPhase 4と同じ合成器でL2グローバル既定、L3種別既定、L4 Profileを解決し、
`--print %()j`の構造化結果から利用可能format、現在のselectorによる選択、推定サイズだけを
表示する。出力先・Storage・Artifactを作らず、外部処理中はthread poolへ退避してappのevent loopを
塞がない。expert modeの予約引数とexecは検査の出力契約・無副作用性と両立しないため明示拒否する。

全Profile共通の開始間隔を`format.probe_min_interval_sec`（既定10秒）で制限し、失敗も間隔へ
含める。入力URLは画面へ再表示せず、Runnerの一次マスク対象として保存ログへの混入を防ぐ。
検査結果からselectorを組み立てる補助は、format組合せの意味を誤って単純化する危険に対して
利得が小さいため実装せず、利用者が表示されたIDをProfileへ明示入力する方式とした。

### 4.15 yt-dlp自動更新と強化スモークテスト

app専用schedulerが`ytdlp.update_cron`（既定`0 4 * * 0`、空文字で無効）の引数なしjobを実行する。
更新全体は専用file lockで直列化し、最新版venvを導入して原子的symlink切替後に次を検査する。

1. 指定venvの`yt-dlp --version`がDB上のversionと一致する
2. verbose出力でyt-dlpがDenoをJS runtimeとして検出する
3. `--simulate`の構造化メタデータを取得できる
4. 公開CC素材を専用Stagingへ実ダウンロードできる
5. probeとdownloadの保存ログに`n challenge solving failed`がない
6. venvに`mutagen` / `yt_dlp_ejs`があり、固定markerのメタデータとthumbnailを実ファイルへ埋め込める

D-015の既定素材はthumbnailを提供しないため、同じ専用Staging内に短いM4Aと検証画像を生成し、
yt-dlp自身の`EmbedThumbnailPP`でcoverを埋め、venv内のmutagenで実体を確認する。metadataは
`--parse-metadata`で固定markerを注入し、元ファイル既存tagでは成功扱いにしない。スモーク専用
ディレクトリは成功・失敗を問わず削除し、Storage、Artifact、通常のTargetへpublishしない。
両yt-dlp経路は`--ignore-config`で外部設定を遮断し、保存前に全HTTP(S) URLを伏せる。DB結果には
安全なreason codeと真偽値だけを保存する。

新版の検査失敗時は、直前版を切り替えずに同じ強化スモークで検査する。直前版が健全な場合だけ
symlinkを戻す。新旧両方が失敗した場合は新版を維持し、両結果を報告する。いずれの新版失敗も
`run_failed` Hookを発火する。手動ロールバックも直前版の検査成功後にだけ切り替える。

## 6. 外部依存（yt-dlp / rclone / ffmpeg）との境界

- yt-dlp: 永続 volume 上の venv に公式 `default` extras 付きでインストール。
  `mutagen`（音声メタデータ・サムネイル埋め込み）等も venv に含め、アプリイメージには焼き込まない
  （要件定義 §5）。導入契約マーカーで旧 venv を検出し、更新時に不足依存を自動修復する
- rclone / ffmpeg / Deno: イメージに焼き込む。バージョンは Dockerfile 内で明示固定し、
  配布物のchecksumを検証する。Denoはyt-dlpのYouTube EJSランタイムとしてPATHから自動検出される
- いずれも CLI を subprocess 経由で呼び出す。Python API・shell 経由の呼び出しは行わない
- rclone は `--use-json-log --log-level INFO --ask-password=false` を共通指定し、必要な転送では
  `--stats` を加える。アプリ側 Task リトライとの二重化を避けるため `--retries 1` と
  `--low-level-retries 1` に抑える。設定ファイルは読まず、`--config /dev/null` と
  `RCLONE_CONFIG_<REMOTE>_<KEY>` の子プロセス限定環境変数を使う
- yt-dlp との出力プロトコル（Phase 3）:
  - `--progress-template "download:SLUICERY_PROGRESS %(progress)j"` で進捗を JSON 行として出力させる
  - `--print "[WHEN:]SLUICERY_PRINT %(...)"`（`%()j` で info dict 全体を JSON 化できる）でメタデータ・
    保存パス等を出力させる。`WHEN` は `--use-postprocessor` と同じ値が使える（`after_move` 等）
  - 上記2つの行頭プレフィックスで stdout を demux する（`downloader/protocol.py`）。プレフィックスの
    無い行は無視する
  - ロケールは `LC_ALL=C` に固定（エラー分類が英語メッセージに依存するため）
  - 子プロセスは新しいプロセスグループで起動し、タイムアウト・キャンセル時はグループ単位で終了させる
    （yt-dlp が子プロセスとして起動する ffmpeg が孤児化しないようにする）
  - 実機（yt-dlp 2026.07.04）で上記テンプレート構文の出力を確認済み
- ファイル名境界（Phase 4、yt-dlp 2026.07.04 で実測）:
  - `--windows-filenames` は `\ / : * ? " < > |` を削除せず、見た目の近い Unicode 文字
    （`⧹ ⧸ ： ＊ ？ ＂ ＜ ＞ ｜`）へ置換した。日本語と絵文字は保持された
  - Windows 予約語そのもの（`CON.mov`）と、拡張子直前のタイトル由来のドット・空白
    （`末尾. .mov`）は残った。ただし sluicery の標準テンプレートは末尾に `[<source_id>]`
    を必須とするため、生成される完全な stem が `CON` 等になることはない
  - `--trim-filenames` はテンプレート末尾の ID まで切り詰めうるため、flat のタイトル部分を
    120 byte に制限した上で使用する。ユーザー入力のディレクトリ要素は `core/naming.py` が
    予約語・禁止文字・末尾ドット/空白を処理する（D-018）

### Phase 16 retention検証（2026-08-16）

Playlist単位の保持ポリシーは既定無効とし、最新N件とM日より古いItemの和集を
dry-runで表示する。有効化と削除実行はどちらも、表示したsnapshotの署名付きtoken、
300秒の有効期限、チェックボックスと確認ダイアログを必須とする。実行直前にpolicy、
Artifact数、候補のArtifact / Target / Storage更新世代、Storage設定fingerprintを再計算し、
変化時は拒否する。execute用dry-runでは実体のsize・mtime・SHA-256・file IDも署名対象にし、
強い識別情報を得られないremote backendは削除対象にしない。

## 7. 設計判断の記録

### D-001: 権限降格に gosu ではなく setpriv（util-linux）を使う

- 日付: 2026-08-08
- 背景: PUID/PGID/UMASK を実行時に反映するには、root で起動してからアプリユーザーに降格する必要がある（要件定義 N-5）
- 選択肢: (a) gosu を GitHub リリースから取得して固定 (b) su-exec（Alpine 系、Debian には無い） (c) util-linux 同梱の setpriv
- 決定: (c)。Debian slim イメージに標準で入っており、追加の外部バイナリ取得・checksum 管理が不要
- 影響: なし

### D-002: ffmpeg は静的ビルドを checksum 検証して導入する

- 日付: 2026-08-08
- 背景: 要件定義 §4.2 で rclone / ffmpeg のバージョンを Dockerfile 内で明示固定することが求められている。apt 経由だと Debian リポジトリの状態に依存し、後から同じバージョンを再現できない
- 選択肢: (a) apt-get install ffmpeg （バージョン追跡が困難） (b) johnvansickle.com の静的ビルドを sha256 固定して取得
- 決定: (b)。取得 URL 自体は「最新の release」を指す固定文字列だが、ビルド時に sha256 を検証するため、上流が更新されればビルドが失敗して気づける（無言で異なるバイナリが混入しない）
- 影響: バージョンを上げる際は `FFMPEG_SHA256` を手動で更新する必要がある
- 補強（2026-08-08）: 取得 URL を `ARG FFMPEG_URL` として build-arg 化した。johnvansickle は最新版を固定名で配布し、旧版はバージョン番号付きファイル名で `old-releases/` 配下に残し続けるため、上流ローテーションで checksum 不一致が発生した場合は `old-releases/` の versioned URL に `FFMPEG_URL` を差し替えるだけで、以前と同一バージョンを再取得できる（イメージの再現性が壊れない）

### D-003: requirements.lock はこのセッションでは生成できていない

- 日付: 2026-08-08
- 背景: `pip-compile --generate-hashes` の実行には pip または Docker デーモンが必要だが、実装セッションの実行環境にはどちらも無かった（pip 未インストール、Docker Desktop の WSL 連携が無効）
- 決定: ハッシュを手で捏造しない。`make lock` ターゲット（Docker + ネットワークがある環境で pip-compile を実行）を用意し、ユーザー側での実行を前提とする
- 影響: `requirements.lock` が生成されるまで `docker compose up` は失敗する。AISTATE.md の未解決 #1 を参照
- 追記（2026-08-08、Phase 2 前半）: 本セッションでも docker デーモンへの権限がなく（socket が root:docker 所有でユーザー未所属）、`make lock` を実行できていない。ユーザー側で `sudo usermod -aG docker $USER` 後、`make lock` → `docker compose up -d --build` の実行を依頼した
- 解決（2026-08-08、Phase 2 後半）: ユーザーが docker グループへの追加を完了。`requirements.lock` を生成し、`docker compose up -d --build` で app / worker-network / worker-compute の起動を確認した（詳細は変更履歴.md、D-010 参照）

### D-004: `SECRET_KEY` はローテーション非対応とする

- 日付: 2026-08-08
- 背景: `storage.credentials_encrypted` を Fernet で暗号化する以上、鍵が変わると復号できなくなる。再暗号化コマンドを実装する選択肢もあった
- 選択肢: (a) 再暗号化コマンドを実装し、旧鍵→新鍵の移行を自動化する (b) ローテーション非対応とし、紛失・変更時はクレデンシャル再入力を促す
- 決定: (b)。Phase 2 の時点では Storage 数も少なく、再暗号化の実装・テストコストに見合わない。鍵指紋（`setting` テーブルに sha256 ハッシュを保存）を照合し、意図しない鍵変更を検知して明確な警告を出すことで、原因不明の復号エラーだけは防ぐ
- 影響: 鍵を変更する運用は、各 Storage の認証情報を手動で再入力する前提になる。README.md / docs/legal.md に明記

### D-005: 運用パラメータを `.env` から `setting` テーブルへ移す

- 日付: 2026-08-08
- 背景: 要件定義 §17 は `STAGING_WARN_PCT` 等を `.env` の一覧に含めていたが、これらは Web UI からの変更が要件で想定されている運用パラメータであり、`.env` 編集＋再起動でしか変更できないのは要件（Web UI からの設定変更）と矛盾する
- 選択肢: (a) 要件定義 §17 の通り `.env` に置く (b) `.env` はインフラ・セキュリティ境界に限定し、運用パラメータは DB の `setting` テーブルに移す
- 決定: (b)。既定値はコード側（`core/settings.py` の `CODE_DEFAULTS`）に定義し、`setting` テーブルにはユーザーが明示的に上書きした項目のみを保存する二層構造とした
- 影響: 要件定義 §17 の環境変数一覧との差分が生じる（本書 §3 参照）。`.env.example` から該当項目を削除した

### D-006: `Task.claim_next()` は単一 UPDATE ... RETURNING でアトミックに実装する

- 日付: 2026-08-08
- 背景: 複数ワーカー（プロセス）が同一 Task を同時に claim してはならない（要件 §8.3）
- 選択肢: (a) `BEGIN IMMEDIATE` で明示的に排他ロックを取ってから SELECT→UPDATE の2文で実装する (b) 候補選定（`WHERE status=queued ORDER BY priority DESC, id ASC LIMIT 1`）と `queued→running` への更新を単一の `UPDATE ... WHERE id IN (...) ... RETURNING` 文にまとめる
- 決定: (b)。PRAGMA で `journal_mode=WAL` と `busy_timeout=5000` を設定済みであり、SQLite は書き込みを直列化するため、単一 UPDATE 文自体がアトミックな排他になる。実装がシンプルで、明示的なロック管理（例外時の unlock 漏れ等）のリスクがない
- 影響: 20〜30スレッドが同一/複数 Task を奪い合う並行テストで二重 claim が発生しないことを確認済み（`tests/test_task_claim_next.py`）

### D-007: DB のタイムスタンプに独自の `UTCDateTime` 型を使う

- 日付: 2026-08-08
- 背景: SQLAlchemy の `DateTime(timezone=True)` は SQLite では tzinfo を保持しない（書き込み時に無言で破棄、読み出し時は naive datetime）。テスト作成中に発覚した
- 選択肢: (a) アプリ側が読み出し後に毎回 `.replace(tzinfo=UTC)` するルールを徹底する (b) `TypeDecorator` でカラム型自体に UTC の付け外しを組み込む
- 決定: (b)。(a) は徹底を人手に頼ることになり、忘れた箇所だけ naive datetime が混入する事故が起きやすい。カラム型に閉じ込めることで、モデル層を使う限り自動的に守られる
- 影響: 書き込み時に naive datetime を渡すと `ValueError` になる（`datetime.now(UTC)` 等、必ず aware で渡す必要がある）

### D-008: Alembic autogenerate は SQLite 上の CHECK 制約を正しく比較できない（既知の制限）

- 日付: 2026-08-08
- 背景: `alembic revision --autogenerate` や `alembic check` を、生成直後の DB に対して実行しても、Enum 由来の CHECK 制約が「削除→再作成」の差分として毎回検出される
- 原因: SQLAlchemy は SQLite の CHECK 制約をリレクションで完全には復元できず、比較対象を構造的に一致させられない（SQLAlchemy/Alembic 側の既知の制限であり、本プロジェクトの実装ミスではない）
- 対応: 実害はない（`upgrade` / `downgrade` 自体は正しく動作する。§9.2 で確認済み）。今後 Phase 3 以降で `alembic revision --autogenerate` を実行する際、生成物に CHECK 制約の削除/再作成が混ざっていたら、実際の変更に無関係なら手で取り除いてからコミットすること（§5.2 の「手で確認・整形」の一環）

### D-009: `user` の2件目禁止はリポジトリ層で担保する

- 日付: 2026-08-08
- 背景: 要件定義は「2件目のユーザー作成を禁止」とだけ規定しており、DB 制約かアプリ層かの選択は実装時判断とされていた（§4.3）
- 選択肢: (a) SQLite の `CHECK` やトリガーでテーブル全体を1行に制限する (b) `UserRepository.create_single()` で作成前に既存行の有無を確認する
- 決定: (b)。SQLite で「テーブル全体で高々1行」を宣言的な制約だけで表現するのは技巧的（トリガーが必要）になり、Phase 2 のリポジトリ層の「呼び出し側が固まっていないものは作らない」方針とも整合しないため、アプリ層のガードで十分と判断した
- 影響: `UserRepository.create_single()` を経由しない生の `session.add(User(...))` では防げない。呼び出し側は必ずリポジトリ経由でユーザーを作成すること

### D-010: `MEDIA_ROOT` の書き込み検証は環境変数の値ではなく固定パスに対して行う

- 日付: 2026-08-08
- 背景: `docker compose up -d --build` による実地検証で発覚。`MEDIA_ROOT` はホスト側の bind mount ソースパスであり、`compose.yaml` は常に `${MEDIA_ROOT}:/mnt/media` でマウントする。コンテナ内から見える実際のパスは常に `/mnt/media` で、`MEDIA_ROOT` の値そのもの（例: `/tmp/foo`）はコンテナ内には存在しない。`config.py` の `Settings` が `MEDIA_ROOT` フィールドの値をそのまま存在・書き込みチェックしていたため、既定値（`/mnt/media`）以外を設定すると起動できなかった
- 選択肢: (a) `MEDIA_ROOT` フィールドの検証をやめる（entrypoint.sh の事前チェックのみに委ねる） (b) 検証対象を固定のクラス定数 `MEDIA_MOUNT_PATH`（`/mnt/media`）に切り替え、`MEDIA_ROOT` フィールド自体は表示・記録用として残す
- 決定: (b)。`sluicery config check` で書き込み可否を可視化する要件（docs/phase2_指示書.md §2.2）は維持しつつ、実際に意味のあるパスを検証する
- 影響: `check_config()` のエラー報告で、モデル全体に対する検証エラー（`loc` が空）を `MEDIA_ROOT` に紐づけて表示するようにした。テストでは `Settings.MEDIA_MOUNT_PATH` を monkeypatch で差し替える

### D-011: `ytdlp_release` テーブルを新設し、`active` は1件をリポジトリ外（`downloader/version.py`）で担保する

- 日付: 2026-08-08
- 背景: 要件定義 §5.3 は yt-dlp の更新履歴（バージョン・日時・結果）を DB に記録することを求めているが、論理設計（§7.1）に対応するテーブルが無かった
- 選択肢: (a) `setting` テーブルに JSON 配列として履歴を積む (b) 専用テーブル `ytdlp_release` を新設する
- 決定: (b)。バージョンごとに `status`（`installed`/`active`/`removed`）や `activated_at`/`deactivated_at` を持たせたいため、単一の JSON 配列よりテーブルの方が扱いやすい。`active` を高々1件に保つ制約は DB では強制せず、`downloader/version.py` の切替処理（`_activate()`）に閉じ込めた。`user` の2件目禁止（D-009）と同じ考え方
- 影響: リポジトリ層（`YtdlpReleaseRepository`）は素の CRUD のみで、複数行にまたがる不変条件を知らない

### D-012: yt-dlp の `install` は明示的な `use` がない限り `current` を切り替えない（初回導入時を除く）

- 日付: 2026-08-08
- 背景: `ytdlp install --version X` で過去バージョンを追加導入したときに、意図せず稼働中のバージョンが切り替わってしまうと事故になる
- 選択肢: (a) `install` は常に導入したバージョンを `current` にする (b) `install` は導入のみ行い、`current` が存在しない（未導入・`broken`）場合に限り自動で `active` にする
- 決定: (b)。稼働中バージョンの切替は `ytdlp use` という別の明示的操作に一本化する。ただし `current` が無い状態のまま install だけ繰り返しても `app` が永遠に `not_installed`/`broken` から復旧できないため、その場合のみ例外的に自動 `active` 化する
- 影響: `ytdlp install --force` は「壊れた `current` の復旧」にも使える（`current` が `broken` なら再インストール後に自動で `active` になるため）

### D-013: yt-dlp 未導入でも `app` は起動し、`worker` は待機ループへ入る（degraded 起動）

- 日付: 2026-08-08
- 背景: yt-dlp の導入前に `app`/`worker` が起動できないと、初回セットアップで `docker compose up -d` しただけでは何も操作できない。また Phase 6 の Task キューが未実装の間、`worker` は実処理を持たず、そのまま終了すると `restart: unless-stopped` により再起動ループに入り、Docker の restart backoff が効き始めてしまう
- 選択肢: (a) yt-dlp が無ければ起動を拒否する (b) `app` は常に起動し、`ytdlp.auto_install` が true ならバックグラウンドで自動導入を試みる。`worker` は yt-dlp が `ready` になるまで待機ループに入り、終了しない
- 決定: (b)。`SECRET_KEY` 未設定時の拒否（設計原則上「即座に気づくべき致命的な設定ミス」）とは性質が異なり、yt-dlp 未導入は運用中に起こりうる正常な状態（自動更新失敗時のロールバック前など）として扱う
- 影響: 自動導入はベストエフォートであり、失敗しても `app` 自体はログを出すだけで動き続ける。`worker` の待機ループはログを初回と状態変化時のみ出す（毎ループ出力すると起動直後にログが埋まる）

### D-014: 未知の yt-dlp エラーメッセージは `failed`（安全側）に分類する

- 日付: 2026-08-08
- 背景: エラー分類ルール（`downloader/errors.py`）は yt-dlp の英語メッセージの部分一致に依存しており、バージョンアップで文言が変わると簡単に外れる

- 決定: (c)。`unavailable` に誤って倒すと自動リトライ対象から外れて放置される。`blocked` に誤って倒すとリトライ回数の上限がいつまでも効かなくなる。`failed` はリトライ回数を消費しつつ既定の上限（`retry.max_attempts`）で最終的に `unavailable` へ落ちるため、誤分類時の実害が一番小さい
- 影響: 実機で新しいエラーパターンを見つけるたびに `ERROR_RULES` へ追記していく運用になる

- 決定: (b)。`ffmpeg -version` / `ffprobe -version` は正常終了し、既存の `trailer_1080p.mov`を `ffprobe -v error -show_format -show_streams -of json` で解析して2 streamと32.995秒のdurationを取得できた。同一素材の `--download-sections "*0-1" --force-keyframes-at-cuts` では `ffmpeg exited with code -11` を再現したため、障害は区間切り出し経路に局在すると判定した
- 影響: Phase 7 verify は現行 ffprobe で実装する。区間取得は現バージョンの既知の制限とし、パイプラインの判定・変換機能には使用しない

### D-037: yt-dlp分類をTaskとTargetの異なる状態軸へ写像する

- 日付: 2026-08-12
- 背景: Taskは1回の実行状態、Targetはコンテンツの永続状態であり、同じ `unavailable` でも意味が異なる
- 決定:

  | yt-dlp分類 | Task | Target |
  |---|---|---|
  | `ok` | `succeeded` | チェーン継続中は `downloading` |
  | `failed` | `failed`（上限まで再試行） | `failed`、`retry_count` を増やす |
  | `unavailable` | `unavailable` | `unavailable` |
  | `blocked` | `blocked`（attempts不変） | `blocked`（retry_count不変） |

- 影響: Target更新は現在状態を条件に含む単一UPDATEとし、後続TaskはTask依存失敗伝播に任せる。エラー時もStagingのファイルは削除しない

### D-038: verifyのdurationは記録だけ行い異常判定に使わない

- 日付: 2026-08-12
- 背景: discover値とffprobe値の比較は破損検知に見えるが、generic extractorの欠損、ライブ、可変長メディアで誤検知しうる
- 決定: ffprobeの `duration` は秒数でpayload / Artifactへ記録するが、Phase 7では成否判定に使用しない。非0 byteとffprobeの正常終了・JSON解析可能性を健全性判定とする
- 影響: duration差分の判定はPhase 13の整合性チェックで再検討する。verify失敗時は理由をpayloadへ残し、Stagingを削除しない

### D-039: publishはStagingを削除せず、同サイズの既存最終名を再開とみなす

- 日付: 2026-08-13
- 背景: publishの最終化後、Task成功記録前にworkerが落ちると、再試行時に最終名だけが既存となる。またArtifact確定前のStaging削除は復旧材料を失う
- 決定: Storageアダプタはpublish成功後もStaging元を保持し、index完了後だけ削除する。publish再試行時に最終名が既存なら、上書きせずサイズが検証済みStaging元と一致する場合だけ前回publish済みとして再開する

### D-040: Artifactはindexでだけ冪等確定しchecksumを計算しない

- 日付: 2026-08-13
- 背景: publish前のArtifact作成は実体とDBを不整合にし、index成功直後のworker停止は再実行時の重複作成を起こしうる。大容量ファイルのチェックサム計算はindexの完了を遅らせる
- 決定: Artifactはpublish後のindexでだけ作成し、`target_id + role + storage_id + relative_path` を一意キーとする。Targetをdownloadedへ遷移した後に、設定が有効な場合だけ該当Stagingファイルを削除する。`checksum` はnullとする
- 影響: indexの再実行は同じArtifactを返す冪等操作となる。Staging削除失敗はArtifact / Target確定を覆さない。checksumはPhase 13の整合性チェックで必要性を再検討する

### D-041: 空のdiscover結果は常に空振りとして扱う

- 日付: 2026-08-13
- 背景: yt-dlpの空結果だけでは、本当に空のPlaylistと一時障害・抽出仕様変更を区別できない。空結果から既存Itemを一括delistedにすると誤判定の影響が大きい
- 決定: 有効なエントリが0件またはyt-dlpがエラー終了した場合はItem、Target、Playlistの最終discover日時を一切変更せず、Runの`empty_result=true`を記録する。エラー時のRun自体はfailedとする。dry-runも同じ差分算出を行うがドメインDBを変更しない
- 影響: 本当に空になったPlaylistは自動delistedにできないため、Run履歴で空振りを利用者へ明示する。非空結果に限り、未出現Itemをdelistedへ、再登場ItemをactiveへCASで遷移する。いずれもTarget / Artifact / 実ファイルは変更しない

### D-042: downloadはStorage単位の事前確認後に最大50 Targetずつ投入する

- 日付: 2026-08-13
- 背景: 数千Targetの5段チェーンを一括生成するとTaskテーブルが急増する。また利用不能なStorageへ同じ失敗を繰り返すTaskを大量生成すべきでない
- 決定: active Itemに属するpendingと再試行上限未満のfailedだけをplaylist_index順で候補とし、出力Storageごとに到達性・書込み・容量を一度確認する。問題がある候補はチェーンを作らずblockedへ遷移する。回復したblockedと再試行可能なfailedはpendingへ戻し、`sync.max_targets_per_run`（既定50）まで投入する
- 影響: 上限超過分はpendingのまま次回へ残し、`targets_remaining`へ記録する。Targetのqueued遷移と5 Task生成は同一transactionとし、並行実行による重複チェーンをCASで拒否する

### D-043: download Runはチェーン投入完了時点で確定する

- 日付: 2026-08-13

- 決定: discover Runは1つのnetwork Taskの結果で確定する。download Runは対象選択・Storage事前確認・チェーン投入が完了した時点で`succeeded`とし、以後の個別成否はTargetで追跡する。今回の投入が0件かつblockedが1件以上なら、過去のdownloaded件数にかかわらず`failed`とする
- 影響: Runの統計は実行完了数ではなく、同期時点の`downloaded` / `failed` / `blocked`分布と投入数・残数を示す。discoverのTask payloadにはPlaylist IDとdry-runだけを保存し、実URLを複製しない

### D-059: Hookは単一のbounded非同期queueとpayload allowlistへ集約する

- 日付: 2026-08-21
- 背景: 各発火点が同期的にDBへ書くとHook障害が本体を止め、複数threadへ無制限に投げると順序・メモリ上限を失う。自由形式payloadは秘密やURLの混入を防ぎにくい
- 選択肢: (a) 各処理から同期記録 (b) 発火ごとに独立thread (c) 単一workerの容量付きqueueとイベント別allowlist
- 決定: (c)。容量1000、単一workerで順序を保ち、失敗・飽和は安全なlogだけを残して本体から隔離する。設定不正は空購読へfallbackし、shutdownはproducer停止後にpending処理をflushする
- 影響: queue飽和時はイベントを落として本体処理を継続する。payloadは将来項目を自動では通さず、イベントごとにallowlist更新と回帰試験が必要になる。Jellyfin / Navidrome等の外部アダプタは実装しない

### D-060: kernel mountは別Compose overlayと実効capabilityの二重条件にする

- 日付: 2026-08-21
- 背景: CIFS / NFSのkernel mountには`SYS_ADMIN`とAppArmor緩和が必要だが、通常運用の全サービスへ付けるとコンテナ隔離を恒常的に弱める。環境変数だけでは利用者や誤設定により機能を有効化できる
- 選択肢: (a)通常Composeの全サービスへ常時付与 (b)環境変数だけで切替 (c)別overlayの固定sentinelと実効capabilityを両方確認し、必要なサービスだけへ付与
- 決定: (c)。`compose.privileged.yaml`を明示指定したapp / worker-networkだけに`SYS_ADMIN` / `DAC_READ_SEARCH`、`apparmor:unconfined`、`rshared` bindを付ける。UI / CLI / adapter factoryは固定sentinelと`/proc/self/status`の実効capabilityが両方揃う場合だけ有効にする
- 影響: compute workerと通常Composeは非特権のまま。CIFS資格情報はtmpfsのmode 600一時ファイルだけを介し、argvへ載せない。ホストのbind元がshared mountでない環境ではoverlay自体が起動できない。外部VMへ接続できず実CIFS / NFSは未検証のため、既定・推奨は引き続きrclone remoteとする

### D-061: SECRET_KEYはbackupへ含めず、別保管と指紋照合を必須にする

- 日付: 2026-08-21
- 背景: DB snapshotには暗号化済みStorage資格情報とPlaylist Cookieが含まれる。archiveへ復号鍵も同梱すると、単一fileの流出だけで全資格情報を復号できる。一方、鍵を含めなければ復旧時の取り違えを検出する必要がある
- 選択肢: (a)DBとSECRET_KEYを同一archiveへ保存 (b)資格情報をbackup対象外にする (c)暗号化DBは保存するが鍵を除外し、SHA-256指紋だけをmanifestとDBで照合する
- 決定: (c)。backup時は現在鍵とDB内部指紋が一致しない場合に停止する。restore時はmanifest、復元DB、現在鍵の指紋を比較し、不一致を常に拒否する。鍵不一致時にmanifest HMACを検証できないoverrideは設けない。archiveはmode 600、出力directoryは700とする
- 影響: 利用者はarchiveと同じSECRET_KEYを別の安全な場所へ保管する必要がある。restoreは上書き前に現状態を自動backupし、全service停止後、鍵で認証したmanifest HMAC、全memberのpositive path / regular file / size / SHA-256、SQLite quick_check、現DB WAL checkpointを最初の書込み前に検証する。configはbackup時点へ同期し、logは含まれる場合だけmergeする。メディア、Staging、yt-dlp venv、`.env`は列挙も変更もしない

### D-062: folder_name変更は署名preview付きの明示移動へ分離する

- 日付: 2026-08-21
- 背景: Playlist名と`folder_name`は独立しているが、通常編集で`folder_name`だけを先に変えると旧pathを失い、要件定義§11.4の明示移動・件数表示・途中再実行を満たせない。remote moveの存在確認だけでは同時作成された移動先を上書きしうる
- 選択肢: (a)名前変更時に自動rename (b)folder_nameだけDB更新 (c)通常編集では保持し、専用画面のpreviewと確認後にArtifact単位で移動
- 決定: (c)。previewは新旧subpath、実体識別情報、DB更新世代、Storage設定fingerprint、移動先不在を期限付き署名tokenへ束縛する。DB snapshotはStorage I/O前に閉じる。実行はDBとfsync済みRun logへmove intentを永続化し、Playlist単位のprocess lockを保持してからlocalのno-replace rename、remoteの`--ignore-existing`を行う。成功ごとにArtifact pathとRun統計をcommitし、全件後だけ`folder_name`を更新する
- 影響: Playlist名の変更は常にfile無操作で、CLI editとconfig overwriteも既存`folder_name`を保持する。move後・DB commit前の停止やremote応答不明は、source不在かつdestinationがintentの強いidentityと一致する場合だけ次回previewで回収する。両方存在・両方不在・identity不一致は自動処理しない。テンプレート外Artifactは移動せず、SMB / remote / mountを含む件数はUIで警告する

### D-063: opt-in重複排除・download claim上限・Run log保持を実設定へ接続する

- 日付: 2026-08-21
- 背景: `dedup_hardlink`、`download.item_concurrency`、`log.retention_days`はschema / 設定値だけでは要件§11.5、N-1、N-6を満たさない。hardlinkは既定動作へ混ぜるとPlaylist独立保持を破る
- 選択肢: (a)項目を廃止 (b)値だけ保持して将来実装 (c)明示opt-inと安全なfallback、worker claim、既知log cleanupへ接続
- 決定: (c)。dedup有効Playlistだけ、同一source ID・Profileの既存Artifactを探し、local / mount adapter間で同一filesystemならno-replace hardlinkを作る。失敗・別filesystem・remoteは通常publishへfallbackしてRun logへ記録する。item concurrencyは全network workerのDOWNLOAD claim数をDBで上限化し、2以上の保存に警告確認を要求する。終了済みRunの`run-<id>.log`と既知runner一次logだけを保持日数後に削除する
- 影響: 既定は独立実体・並列1・30日保持のまま。retention監査logは全intentが完了したものだけ期限後に削除し、未完了intent、未知file、symlink、実行中TaskのあるRun logはcleanup対象外。並列度変更はworker再起動後に反映され、複数network workerを起動してもDB上限を超えてDOWNLOADをclaimしない
