# 1. 概要

## 1.1 目的

登録したプレイリスト（動画・音楽）の内容をローカルまたはネットワークストレージに取得・保持し、定期実行で差分を追従する自己ホスト型サーバーアプリケーション。

## 1.2 想定利用者

単一の技術者。yt-dlp の挙動とオプション体系を理解しており、細かい調整を自ら行う。したがって **UI は「わかりやすさのために選択肢を削る」方向ではなく、「調整可能な項目を最大限露出する」方向で設計する**。

## 1.3 前提と制約

私的使用の範囲を超えないことを設計上の制約とする。

- 外部公開・多人数利用は非対応。そのための機能（マルチユーザー、共有リンク、公開API）は実装しない
- DRM で保護されたコンテンツの取得は対象外。回避手段は実装しない
- 認証は単一ユーザーのみ。2件目のユーザー作成を禁止する

## 1.4 設計原則

判断に迷った場合、以下の優先順で決めること。

1. **ローカルのデータを失わない。** 配信元での削除・非公開化がローカルファイルの削除を引き起こしてはならない。自動削除は明示的にオプトインされた機能に限る
2. **ユーザーの操作を尊重する。** ユーザーがファイルシステム上で行った操作（移動・リネーム・削除）をアプリが勝手に打ち消さない
3. **残骸を残さない。** アンインストール時にホスト上へ痕跡を残さない。宣言されたマウント以外にホストへ書き込まない
4. **調整可能性 > 単純さ。** ただし既定値は保守的に置く
5. **再現性。** 同じ手順で同じ環境が再構築できること

## 1.5 スコープ外（現バージョン）

- メディアサーバー（Jellyfin / Navidrome 等）との実連携 → 拡張点のみ用意
- トランスコード / 再エンコード → パイプラインの受け口のみ用意
- 通知（メール / Webhook） → フックのみ用意
- マルチユーザー、権限管理
- モバイルアプリ、外部公開

# 2. 用語

| 用語 | 定義 |
|---|---|
| Playlist | 監視対象のURL（プレイリスト、チャンネル、単一動画のいずれでも可）を表す登録単位 |
| Profile | yt-dlp オプションの名前付きテンプレート。出力先ストレージとサブパスを併せ持つ |
| Item | Playlist 配下の論理的な1本（yt-dlp の video ID 単位）。ファイルパスを持たない |
| Target | Item × Profile の組。取得状態を持つ |
| Artifact | Target が生成した実体ファイル。1 Target に複数存在しうる（元ファイル + 派生ファイル） |
| Task | ワーカーが実行する作業単位 |
| Run | ユーザーまたはスケジューラが起動した一連の実行。複数 Task を含む |
| Storage | 保存先の定義。`local` または `remote`（rclone リモート） |
| Staging | ダウンロードと後処理を行う一時領域。常にローカル |
| Publish | Staging から Storage へ成果物を移す工程 |
| Discover | プレイリスト構成をスキャンし、Item の増減を検出する工程 |
| Delisted | プレイリストから外れた Item の状態。ファイルは削除しない |

# 4. 配布と再現性

## 4.1 セットアップ手順（これが動くこと）

```bash
git clone <repo> sluicery
cd sluicery
cp .env.example .env
$EDITOR .env          # 最低限 SECRET_KEY と保存先パスを設定
docker compose up -d
```

## 4.2 再現性の担保

- ベースイメージは **digest でピン留め**する（`python:3.12-slim@sha256:...`）
- Python 依存は `requirements.in` から `pip-compile --generate-hashes` で `requirements.lock` を生成し、`--require-hashes` でインストールする
- rclone / ffmpeg のバージョンを Dockerfile 内で明示的に固定する
- **コンテナ内に状態を持たない。** 全ての永続データは volume または bind mount に外出しする
- `.env.example` に全設定項目を、既定値とコメント付きで記載する

## 4.3 ホストへの影響範囲

**アプリがホスト上に作成するものは、compose が宣言した volume と bind mount のみとする。**

`docs/footprint.md` に、ホスト上に作られるもの（コンテナ、イメージ、ネットワーク、volume、bind mount 先）を全列挙すること。

## 4.4 Makefile

以下のターゲットを用意する。

| ターゲット | 動作 |
|---|---|
| `make up` | ビルドして起動 |
| `make down` | 停止（データは残す） |
| `make logs` | ログ追従 |
| `make shell` | app コンテナにシェル接続 |
| `make sync` | 全プレイリストの同期を即時実行 |
| `make backup` | DB + config + シークレットを単一アーカイブに固める |
| `make restore FILE=...` | バックアップから復元 |
| `make purge` | **削除対象を一覧表示して確認を取った上で**、コンテナ・イメージ・volume・ネットワークを削除 |

`make purge` は、削除されるもの・削除されないもの（bind mount 先のメディア本体）を明示してから実行すること。

# 5. yt-dlp のバージョン管理

## 5.1 方針

**アプリのバージョン（gitタグ、固定）と yt-dlp のバージョン（追従、可変）を分離する。**

yt-dlp は配信サイトの仕様変更で頻繁に壊れるため、イメージに焼き込むとイメージ再ビルドなしに復旧できなくなる。

## 5.2 実装

- yt-dlp は **永続volume上の venv**（`/data/ytdlp-venv`）にインストールする。イメージには含めない
- エントリポイントで venv の存在と yt-dlp の起動可否を確認し、無ければインストールする
- CLI を subprocess で実行する。Python API（`yt_dlp.YoutubeDL`）は使わない
  - 理由1：アプリと同一プロセスに yt-dlp を同居させるとバージョン分離が成立しない
  - 理由2：オプションを dict に変換する層が挟まると、新オプションへの追従がアプリ側の改修待ちになり、自由度が損なわれる
- 進捗は `--progress-template` で JSON 行を出力させ、`--newline` と併せて標準出力をパースする

## 5.3 自動更新

- 既定で週次。スケジュールは設定可能。無効化も可能
- 更新後に**スモークテスト**を実行する：既知の公開URL（設定可能、既定は Creative Commons のもの）に対する `--simulate --skip-download`
- スモークテスト失敗時は**直前バージョンへ自動ロールバック**し、`run_failed` フックを発火する
- 更新履歴（バージョン、日時、結果）を DB に記録する
- UI に現在バージョン、最終更新日時、手動更新ボタン、手動ロールバックボタンを置く

# 6. ストレージ設計

## 6.1 モデル

Storage は2種類のアダプタで抽象化する。

| kind | 実装 | 特権 |
|---|---|---|
| `local` | コンテナ内から見えるパスへの直接書き込み | 不要 |
| `remote` | rclone のリモート定義（SMB / NFS / WebDAV / SFTP / S3 等）経由の転送 | 不要 |

**既定かつ推奨は `remote`（ユーザースペース転送）。** カーネルマウント方式（§6.6）はオプトイン。

## 6.2 パイプライン

```
[download]  Staging(ローカル)へ取得
     ↓
[verify]    ffprobe による健全性確認、サイズ・長さの記録
     ↓
[postprocess]  拡張点。現バージョンは空（素通し）
     ↓
[publish]   Storage アダプタ経由で最終保存先へ移動
     ↓
[index]     Artifact レコードを確定、フック発火
```

Staging を必ず経由する理由：

1. ネットワークストレージ上で直接 yt-dlp / ffmpeg を動作させると遅く、断線時に破損する
2. 将来のトランスコードは Staging 上で完結させるのが自然であり、この構造が前提になる
3. 未完成ファイルが最終保存先に現れない

**ローカル Storage の場合も Staging を経由する**（同一ファイルシステム上なら rename で済むため、コストはほぼ発生しない）。

## 6.3 Staging 領域

- パスは `.env` で指定。既定 `/data/staging`
- 起動時に前回の残骸（対応する Task が存在しないファイル）を検出し、UI に一覧表示する。**自動削除はしない**
- 容量監視：使用率が警告閾値（既定80%）を超えたら UI に警告、停止閾値（既定90%）を超えたら新規ダウンロードの投入を停止する。閾値は設定可能
- 停止中は Task を `blocked` 状態にし、**リトライ回数を消費させない**

## 6.4 Storage 定義（UI から管理）

共通項目：

- 表示名
- kind（`local` / `remote`）
- 有効/無効

`local` の項目：

- パス（コンテナ内から見えるパス）

`remote` の項目：

- プロトコル（smb / nfs / webdav / sftp / s3 …）
- ホスト、シェア名/パス、ポート
- 認証情報（ユーザー名、パスワード、ドメイン、鍵など。プロトコル依存）
- 追加オプション（rclone のバックエンド固有オプションを自由入力）

共通の検証：保存時に以下を実行し、結果を保持する。

- 疎通確認
- 認証確認
- ディレクトリ一覧取得
- テストファイルの書き込み・読み出し・削除

UI から任意タイミングで再実行できる「接続テスト」ボタンを置き、**4段階を個別に判定して表示する**（どこで失敗したかが分かること）。

空き容量を取得できる場合は UI に表示し、閾値を下回った場合に当該 Storage を publish 先とする Task を `blocked` にする。

## 6.5 クレデンシャルの扱い

- `.env` の `SECRET_KEY` を鍵として Fernet で暗号化し、DB に保存する
- **`SECRET_KEY` が未設定の場合、起動を拒否する。** 自動生成して黙って動作させてはならない（鍵紛失時に復号不能になるため）
- UI では write-only。設定後は「設定済み」表示のみとし、平文を返却しない
- ログ、エラーメッセージ、コマンドラインプレビュー、UI表示から**自動マスクする**（マスク処理は出力の共通層に置き、各所での付け忘れが起きない構造にする）
- 設定エクスポートに含めない。インポート時は再入力を求める
- rclone の設定ファイルは**起動時に tmpfs 上へ生成**し、平文をディスクに残さない。または rclone に環境変数経由で渡す
- バックアップにクレデンシャルを含める場合、`SECRET_KEY` も併せて退避する必要がある旨をドキュメントに明記する

## 6.6 カーネルマウント方式（オプトイン）

compose の `privileged` プロファイルを明示的に有効化した場合のみ、Storage kind として `mount`（コンテナ内で `mount -t cifs` / `mount -t nfs` を実行）を選択可能にする。

必要な設定（compose の当該プロファイルに記述）：

```yaml
cap_add:
  - SYS_ADMIN
  - DAC_READ_SEARCH
security_opt:
  - apparmor:unconfined
```

加えて、マウントポイントを shared propagation で bind mount する必要がある。

**この方式のトレードオフを `docs/storage.md` と UI 上で明示すること。**

- SYS_ADMIN は実質 root 相当の権限であり、コンテナの隔離が大幅に弱まる
- ホストの名前空間にマウントが漏れるため、**コンテナを強制削除するとホスト側にマウント残骸が残る**（ホストで `umount` が必要）。これは本プロジェクトの設計原則3に反する
- ホストのディストリビューションや AppArmor 設定によっては追加の調整が必要

既定では無効であり、有効化しない限りこの kind は UI の選択肢に現れないこと。

# 7. データモデル

SQLite。以下は論理設計であり、カラム名・型の細部は実装時に調整してよい。

## 7.1 テーブル

### user
単一ユーザー。2件目の作成を禁止する。

```
id, username, password_hash, created_at, updated_at, last_login_at
```

### storage
```
id, name, kind(local|remote|mount), enabled,
config_json,              -- 非機密設定
credentials_encrypted,    -- Fernet 暗号化
last_check_at, last_check_result_json,
created_at, updated_at
```

### profile
名前付きの取得設定テンプレート。

```
id, name, description,
kind(video|music|other),        -- 既定値セットの選択と UI 表示上の分類
ytdlp_args,                     -- 自由入力の yt-dlp オプション文字列
format_selector,                -- --format 相当（構造化して別管理）
output_template,                -- layout_strategy=custom 時のみ有効
layout_strategy(flat|custom),
audio_extract, audio_format, audio_quality,
container, embed_metadata, embed_thumbnail, embed_chapters,
subtitle_langs, subtitle_auto, subtitle_embed,
expert_mode(bool),              -- 予約引数の上書きを許可するか
allow_exec(bool),               -- --exec の許可（.env でも許可が必要）
concurrent_fragments,
postprocess_chain_json,         -- 拡張点。現バージョンは空配列
created_at, updated_at
```

### playlist
```
id, name, folder_name, url, enabled,
kind_hint(video|music|mixed),
ytdlp_args,                     -- プレイリスト固有の追加オプション
discover_cron, download_cron,   -- null ならグローバル既定を使用
paused(bool),
retention_policy_json,          -- 既定 null（無効）
dedup_hardlink(bool),           -- 既定 false
created_at, updated_at, last_discover_at, last_download_at
```

`folder_name` は `name` とは独立に保持する。`name` の変更で自動的にフォルダをリネームしない（§11.4）。

### playlist_profile
Playlist と Profile の関連。**出力先はこの組に紐づく。**

```
id, playlist_id, profile_id,
storage_id, subpath,            -- 出力先。subpath はテンプレート可（既定 "{playlist.folder_name}"）
enabled, sort_order,
created_at, updated_at
UNIQUE(playlist_id, profile_id)
```

Playlist は1件以上の Profile を持つ。多くの場合1件。

### item
Playlist 配下の論理的な1本。**ファイルパスを持たない。**

```
id, playlist_id, source_id, source_url,
title, uploader, duration, upload_date, playlist_index,
membership(active|delisted),
metadata_json,
first_seen_at, last_seen_at, delisted_at,
created_at, updated_at
UNIQUE(playlist_id, source_id)
```

`membership` は「プレイリストに存在するか」のみを表し、取得状態とは独立させる。

### target
Item × Profile。取得状態を持つ。

```
id, item_id, playlist_profile_id,
status, retry_count, last_error, last_attempt_at,
blocked_reason,
downloaded_at,
created_at, updated_at
UNIQUE(item_id, playlist_profile_id)
```

### artifact
実体ファイル。1 Target に複数存在しうる。

```
id, target_id, role(source|derived),
storage_id, relative_path, absolute_path_cache,
container, format_id, video_codec, audio_codec,
filesize, duration, checksum,
produced_by_task_id,
verified_at, missing_since,
created_at, updated_at
```

現バージョンで生成されるのは `role=source` のみ。`derived` は将来のトランスコード用。

### task
```
id, type, target_ref_type, target_ref_id, payload_json,
worker_class(network|compute),
priority, status, depends_on_task_id,
attempts, max_attempts,
scheduled_at, started_at, finished_at,
error_message, log_excerpt,
run_id
```

`type`: `discover` / `download` / `verify` / `postprocess` / `publish` / `index` / `integrity_check` / `retention` / `update_ytdlp`

### run
```
id, trigger(manual|schedule|api), kind, playlist_id(nullable),
status, started_at, finished_at,
stats_json,     -- new/downloaded/failed/delisted/skipped 件数
log_path
```

### setting
```
key, value_json, updated_at
```

### event_log
フック発火の記録（拡張点の動作確認用）。

```
id, event_type, payload_json, created_at, delivered_json
```

## 7.2 状態遷移

### item.membership

```
(新規検出) → active
active → delisted     : discover で当該 source_id が現れなかった場合
delisted → active     : 再びプレイリストに現れた場合
```

**delisted への遷移は Artifact に一切影響しない。ファイルを削除しない。**

### target.status

```
pending      : 未取得。ダウンロード対象
queued       : Task 投入済み
downloading  : 取得中
processing   : verify / postprocess / publish 実行中
downloaded   : 完了。Artifact あり
failed       : 一時的失敗。リトライ対象
unavailable  : 回復不能（地域制限、削除済み、上限到達）。自動リトライ対象外
blocked      : 外的要因で保留（容量不足、ストレージ到達不能）。リトライ回数を消費しない
missing      : downloaded だったが Artifact の実体が見つからない
ignored      : ユーザーが意図的に対象外とした。自動処理しない
```

遷移規則：

- `failed` は次回実行時に再試行。`retry_count` が上限（既定5）に達したら `unavailable`
- `blocked` は原因解消後に自動で `pending` に戻す
- `missing` からの自動再取得は**既定で無効**。Playlist 単位でオプトイン可能
- `ignored` はユーザー操作でのみ設定・解除される

# 8. 同期ロジック

## 8.1 二相同期

同期を Discover と Download の2フェーズに分離する。それぞれ独立にスケジュールできる（§10）。

### Phase 1: Discover

1. `yt-dlp --flat-playlist` でプレイリストの現在の構成を取得する
2. 取得結果が**空またはエラーの場合、以降の処理を中止する**（非公開化・一時障害による誤った delisted 判定を防ぐ）
3. 得られた各エントリについて Item を upsert し、`last_seen_at` を更新する
4. 新規 Item は、有効な各 playlist_profile に対して Target を `pending` で作成する
5. 今回のスキャンに現れなかった `active` な Item を `delisted` に遷移させる
6. Run の統計を記録する

**Discover はファイルを一切操作しない。**

### Phase 2: Download

1. `status = pending` または（`failed` かつ再試行可能）な Target を、優先度順に取得する
2. Storage の到達性と空き容量を確認する。問題があれば `blocked` にして次へ
3. Target ごとに Task チェーン（download → verify → postprocess → publish → index）を投入する
4. Task は個別の source_url に対して実行する（プレイリスト全体を再走査しない）

## 8.2 タスクパイプライン

- `depends_on_task_id` で直列の依存を表現する
- `worker_class` でキューを分離する。ネットワーク律速と CPU/GPU 律速を混在させない
- Task の失敗は後続 Task をキャンセルし、Target を `failed` にする
- 途中失敗時、Staging 上の中間ファイルは**残す**（再開のため）。孤立判定は §6.3 に従う

## 8.3 排他制御

- 同一 Playlist に対する Discover / Download の並行実行を禁止する
- 同一 Target に対する Task の重複投入を禁止する
- ワーカーは DB 上で Task をアトミックに claim すること

# 9. yt-dlp オプションの合成モデル

## 9.1 レイヤー

後段が前段を上書きする6層構造とする。

| 層 | 内容 | 変更主体 |
|---|---|---|
| 1 | **予約引数** | アプリ固定。ユーザー変更不可（原則） |
| 2 | グローバル既定 | 設定画面 |
| 3 | 種別既定（video / music） | 設定画面 |
| 4 | Profile | Profile 編集画面 |
| 5 | Playlist 個別 | Playlist 編集画面 |
| 6 | 手動実行時の一時上書き | 実行ダイアログ |

## 9.2 コマンドラインプレビュー（必須）

UI に**最終的に組み立てられたコマンドライン全文**を表示する機能を設ける。各引数について、**どの層に由来するかを併記する**こと。階層化されたオプション合成はプレビューなしでは debug 不能になるため、これは必須要件とする。

クレデンシャルは §6.5 のマスク処理を通すこと。

## 9.3 予約引数とガード

アプリが管理し、上書きされるとファイル追跡が壊れる引数を「予約引数」とする。

```
--paths, -P, --output, -o, --print, -O, --progress-template,
--download-archive, --load-info-json, --exec, --exec-before-download
```

**ガード方針（C案）**：

- 既定では、予約引数と衝突する指定を**バリデーションエラーとして拒否**する
- Profile 単位で `expert_mode` を有効にすると、警告を表示した上で通す
- `--exec` / `--exec-before-download` は**別扱い**とする。コンテナ内での任意コマンド実行に相当するため、`.env` の `ALLOW_EXEC=true` と Profile の `allow_exec` の**両方**が有効な場合にのみ許可する

`--output` については、`layout_strategy = custom` を選択した場合に限り正規の入力経路として開放する（§11.1）。

## 9.4 プロファイルの適用

- Playlist は1件以上の Profile を持つ（`playlist_profile`）
- 1件の場合が大半であり、**1対1のケースが最も単純に動作すること**
- Profile が複数の場合、同一の Item に対して Profile ごとに独立した Target と Artifact が生成される
- Profile の設定変更は、それを参照する全 Playlist に波及する。UI 上で「この Profile を参照している Playlist 一覧」を表示し、変更前に影響範囲が分かるようにする
- Playlist 側で「この Profile の設定を継承せず、この Playlist 専用の値を使う」項目を指定できること（層5による上書き）

## 9.5 既定値

グローバル既定（設定画面で変更可）：

| 項目 | 既定値 |
|---|---|
| アイテム並列度 | 1 |
| `--concurrent-fragments` | 3 |
| `--sleep-requests` | 1.5 |
| `--sleep-interval` / `--max-sleep-interval` | 3 / 12 |
| `--limit-rate` | 8M |
| `--retries` / `--fragment-retries` | 5 / 10 |
| リトライ上限（アプリ側） | 5 |

video 種別の既定：

| 項目 | 既定値 |
|---|---|
| format | `bv*[height<=1080]+ba/b[height<=1080]/b` |
| コンテナ | mkv |
| 埋め込み | メタデータ、サムネイル、チャプター |
| 字幕 | 手動字幕のみ `ja,en` を埋め込み。自動生成字幕は取得しない |

music 種別の既定：

| 項目 | 既定値 |
|---|---|
| format | `bestaudio/best` |

## 9.6 フォーマット検査機能

任意のURLに対して `--simulate` と `-F` 相当を実行し、以下を UI に表示する機能を設ける。

- 利用可能なフォーマット一覧
- 現在の format selector で選択されるフォーマット
- 推定ファイルサイズ

Profile 編集画面から直接呼び出せること。

## 9.7 Cookie の扱い

- 自動ジョブでの Cookie 利用は**既定で無効**
- 使用する場合は Playlist 単位のオプトインとし、UI に注意喚起（アカウントに紐づく大量アクセスは停止リスクがある旨）を表示する
- Cookie ファイルは §6.5 と同様に暗号化保存し、実行時のみ tmpfs 上へ展開する

# 10. スケジューリング

## 10.1 基本

- **ホストの cron / systemd timer を一切使わない。** APScheduler で完結させ、ジョブストアを SQLite に置く
- タイムゾーンは `.env` で指定（既定 `Asia/Tokyo`）。cron 式は指定TZで解釈する

## 10.2 Discover と Download の分離

**独立したスケジュールを持たせること。** 例：検出は1時間ごと、取得は深夜帯のみ、という運用を可能にする。

| 対象 | グローバル既定 |
|---|---|
| Discover | 6時間ごと |
| Download | 6時間ごと |
| Integrity check | 日次 |
| yt-dlp update | 週次 |

Playlist 単位で cron 式による上書きが可能（`discover_cron` / `download_cron`）。

## 10.3 実行制御

- **実行可能時間帯の制限**（例：01:00–06:00 のみダウンロード可）。この時間外は Task を投入しない
- **ジッター**：複数 Playlist が同時刻に集中しないよう、±N分（既定5分、設定可）のランダム遅延を入れる
- **一時停止**：Playlist 単位で `paused` を設定でき、スケジュール対象から外れる
- **手動実行**：全体 / Playlist単位 / Target単位。実行時に一時オプション上書きが可能（層6）
- **キャンセル**：実行中の Run および Task をキャンセルできる。サブプロセスを確実に終了させること
- UI に**次回実行予定時刻**を表示する

## 10.4 起動時の挙動

- 停止中に予定時刻を過ぎたジョブについて、`misfire_grace_time` を設定し、無制限に積み上がらないようにする（既定：直近1回のみ実行）
- 前回異常終了で `running` のまま残った Task / Run を起動時に検出し、`failed` に落として UI に表示する

# 11. ファイルレイアウトと整合性

## 11.1 レイアウト戦略

`layout_strategy` は Profile が持つ。現バージョンで実装するのは `flat` と `custom`。

**`flat`（既定）**

```
video : <storage.path>/<subpath>/YYYY-MM-DD タイトル [<source_id>].<ext>
music : <storage.path>/<subpath>/NNN トラック名 [<source_id>].<ext>
```

`subpath` の既定は `{playlist.folder_name}`。テンプレート変数を使用できる。

**`custom`**

ユーザーが `--output` テンプレートを指定する。ただし以下をバリデーションで強制する。

- **末尾（拡張子の直前）に `[%(id)s]` を含むこと。** ファイル名先頭でのソートを妨げないため、ID は末尾に置く

**ディレクトリ構造はツリー型とする。** Playlist ごとにフォルダを切る。フラット配置＋インデックス方式は採用しない。

将来の `jellyfin` / `navidrome` は拡張点（§14.2）として追加できるようにインターフェースを定義する。

## 11.2 ファイル名のサニタイズ

SMB 経由の Windows クライアントからの参照を前提とし、**最も厳しい基準に合わせる**。

- 禁止文字 `\ / : * ? " < > |` を置換する
- 制御文字を除去する
- 末尾のドット・空白を除去する
- Windows 予約語（`CON` `PRN` `AUX` `NUL` `COM1-9` `LPT1-9`）を回避する
- パス全体の長さ上限を考慮し、必要ならタイトル部分を切り詰める（`[<source_id>]` と拡張子は必ず残す）
- Unicode 正規化（NFC）を行う

## 11.3 整合性チェックと relink

ユーザーはエクスプローラー等から**ファイルを移動・リネーム・削除する**ことが想定される。パスの存在確認だけでは、移動を削除と誤認する。

チェック手順：

1. `artifact.relative_path` の実在を確認する
2. 見つからない場合、**同一 Storage 配下を `[<source_id>]` で再走査する**
3. 発見したら DB のパスを更新する（**relink**）。ファイルは動かさない
4. 再走査でも見つからない場合のみ、Artifact に `missing_since` を記録し、Target を `missing` にする

`missing` の扱いは Playlist 単位で選択する。

| 選択肢 | 動作 |
|---|---|
| 放置（**既定**） | 状態を記録するのみ |
| 再取得 | Target を `pending` に戻す |
| 無視 | Target を `ignored` にし、以後の処理対象から外す |

**ユーザーがリネームで `[<source_id>]` を消した場合、relink はできない。** 救済として、UI に「孤立ファイルと missing な Target の手動リンク」画面を設ける（Storage 配下の未追跡ファイル一覧と、missing な Target の一覧を並べ、手動で対応付ける）。

整合性チェックは**読み取り専用**であり、いかなる場合もファイルを削除・移動しない。

## 11.4 Playlist 名の変更

- `folder_name` は `name` と独立に保持する
- `name` の変更で既存フォルダを**自動リネームしない**（既定）
- UI から明示的に「フォルダも移動する」を選択できる。実行前に対象ファイル数を表示し、SMB 越しの大量ファイル移動は失敗しうる旨を警告する。失敗時は途中経過を DB に反映し、再実行可能にする

## 11.5 重複の扱い

- **既定は Playlist ごとに独立して保持する。** 同じ動画が複数の Playlist に含まれる場合、それぞれのフォルダに実体を持つ
- Playlist 単位のオプション `dedup_hardlink` を有効にすると、同一 `source_id` かつ同一 Profile の既存 Artifact が**同一ファイルシステム上に**存在する場合、2件目をハードリンクで作成する
- ハードリンクが不可能な条件（異なるファイルシステム、`remote` Storage）では、自動的に通常コピーにフォールバックし、その旨をログに記録する

## 11.6 保持ポリシー（retention）

- 機能として用意するが、**既定は無効**
- Playlist 単位で「最新N件のみ保持」「M日より古いものを削除」を設定できる
- 有効化時、および実行時に**ドライラン（削除対象の一覧表示）を必須**とし、確認を経なければ実行しない
- 削除された Artifact に対応する Target は `ignored` とし、再取得の対象にしない

# 12. 認証

- 単一ユーザーのアプリ内認証
- 初回起動時、`.env` の `ADMIN_USERNAME` / `ADMIN_PASSWORD` でユーザーを作成する。`ADMIN_PASSWORD` 未設定の場合はランダム生成し、**起動ログに1回だけ出力する**
- パスワードは argon2 でハッシュ化する
- セッションは Cookie（`HttpOnly`, `SameSite=Lax`, `Secure` は設定で切替）
- ログイン試行のレート制限（既定：5回失敗で15分ロック）
- UI からパスワード変更が可能
- HTTPS 終端はリバースプロキシの責務とする。アプリは単一ポートで HTTP を待ち受ける
- 2件目のユーザー作成を禁止する

# 14. 拡張点

以下は**インターフェースのみ実装し、具体的なアダプタは空実装または未実装**とする。将来の追加時に既存コードの改修が最小で済む形にすること。

## 14.1 イベントフック

発火するイベント：

```
item_discovered, item_delisted,
target_downloaded, target_failed,
run_started, run_finished, run_failed,
artifact_published, artifact_missing,
storage_unreachable, ytdlp_updated, ytdlp_rollback
```

- 購読側は `config/hooks.yaml` で有効化する
- 発火は非同期とし、フックの失敗が本体処理に影響しないこと
- 現バージョンでは `event_log` テーブルへの記録のみを行う組み込みフックを1つ用意する（動作確認用）
- 将来ここに追加される想定：Jellyfin ライブラリスキャン、Navidrome スキャン、Webhook 通知、メール通知

## 14.2 レイアウト戦略

`LayoutStrategy` インターフェースを定義する。

```python
class LayoutStrategy(Protocol):
    name: str
    def output_template(self, ctx: LayoutContext) -> str: ...
    def validate(self, ctx: LayoutContext) -> list[ValidationError]: ...
```

実装するのは `flat` と `custom`。`jellyfin` / `navidrome` は将来追加。

## 14.3 後処理（トランスコード）

`PostProcessor` インターフェースを定義する。

```python
class PostProcessor(Protocol):
    name: str
    worker_class: str          # "compute"
    def applies_to(self, artifact: Artifact) -> bool: ...
    def run(self, artifact: Artifact, workdir: Path) -> list[Artifact]: ...
```

- Profile の `postprocess_chain_json` に処理チェーンを定義できる構造にする。現バージョンでは常に空
- 出力は `role=derived` の Artifact として登録される
- 元ファイルを保持するか置換するかを、後処理定義ごとに指定できる構造にしておく
- Task type `postprocess` と `worker-compute` キューは**現バージョンから存在させる**（空を通すだけでよい）

**compose に NVENC 用の GPU 割り当て設定をコメントアウトで配置しておくこと。**

```yaml
# worker-compute:
#   deploy:
#     resources:
#       reservations:
#         devices:
#           - driver: nvidia
#             count: 1
#             capabilities: [gpu]
```

## 14.4 ストレージアダプタ

`StorageAdapter` インターフェースを定義する。

```python
class StorageAdapter(Protocol):
    def test_connection(self) -> ConnectionTestResult: ...   # 4段階
    def publish(self, src: Path, dest_rel: str) -> PublishResult: ...
    def exists(self, rel: str) -> bool: ...
    def list_recursive(self, rel: str) -> Iterator[RemoteFile]: ...
    def move(self, src_rel: str, dest_rel: str) -> None: ...
    def free_space(self) -> int | None: ...
```

実装：`local`、`remote`（rclone）。`mount` はオプトイン時のみ。

# 15. 設定のエクスポート / インポート

- 対象：Playlist、Profile、playlist_profile、Storage（クレデンシャルを除く）、グローバル設定
- 形式：YAML 単一ファイル

# 16. 非機能要件

| ID | 要件 |
|---|---|
| N-1 | アイテム並列度は既定1。設定変更可だが2以上で警告を表示する |
| N-2 | 1件の失敗が全体を停止させない。ただし1 Playlist 内の全件失敗は Run を `failed` とする |
| N-3 | 同一設定での再実行が副作用を生まない（冪等）。中断からの再開が可能（`--continue`） |
| N-4 | ネットワークストレージ断線時、書き込み失敗を `blocked` として扱い、リトライ回数を消費しない |
| N-5 | `PUID` / `PGID` / `UMASK` を `.env` で設定でき、生成ファイルの所有者・権限を制御できる |
| N-6 | ログは Run 単位でファイル出力。保持期間は既定30日、設定可能 |
| N-7 | DB は WAL モード。ワーカーとの同時アクセスでロック競合を起こさない設計とする |
| N-8 | サブプロセスは必ずタイムアウトを持ち、孤児プロセスを残さない |
| N-9 | コンテナの再作成後も、volume が残っていれば状態が完全に復元される |
| N-10 | 全ての外部入力（URL、オプション文字列、パス）をバリデーションする。シェルインジェクションを許さない（`shell=True` を使わない） |

# 19. 受け入れ条件

1. `git clone` → `cp .env.example .env` →（`SECRET_KEY` 設定）→ `docker compose up -d` で起動する
2. `SECRET_KEY` 未設定時、明確なエラーメッセージを出して起動を拒否する
3. 初回アクセスでログインでき、Storage / Profile / Playlist を登録できる
4. Storage の接続テストが4段階で個別に判定・表示される
5. Profile 編集画面でコマンドラインプレビューが表示され、各引数の由来層が分かる
6. 予約引数を Profile に入力すると拒否される。`expert_mode` を有効にすると警告付きで通る
7. `ALLOW_EXEC=false` の状態では、`allow_exec` を有効にしても `--exec` が拒否される
8. 手動実行で discover → download が動き、Staging を経て指定 Storage にファイルが生成される
9. 同じ Playlist を再実行して、新規0件・重複ダウンロード0件になる
10. 1つの Playlist に video / music の2 Profile を割り当てると、同一 Item から2つの Artifact が別々の Storage / subpath に生成される
11. Profile が1件のみの場合も、同じ経路で問題なく動作する
12. プレイリストから1件外した状態で discover を実行すると、当該 Item が `delisted` になり、**ファイルは残る**
13. ファイルを別フォルダへ移動した後に整合性チェックを実行すると、`[<source_id>]` により relink され、`missing` にならない
14. ファイルを削除した後に整合性チェックを実行すると `missing` になるが、**自動再取得されない**（既定）
15. Storage を到達不能にすると Target が `blocked` になり、retry_count が増えない。復旧後に自動で `pending` に戻る
16. Discover と Download に別々の cron を設定でき、独立して実行される
17. 実行可能時間帯を設定すると、その時間外に Download Task が投入されない
18. 取得失敗した Target が UI に表示され、個別再試行できる
19. Playlist 名を変更してもフォルダは移動しない。明示操作でのみ移動する
20. retention を有効化すると、ドライランの確認を経なければ削除が実行されない
21. 設定をエクスポート → DB を消して再構築 → インポートで、Playlist / Profile / Storage 構成が復元される（クレデンシャルは要再入力）
22. クレデンシャルが UI・ログ・コマンドラインプレビュー・エクスポートのいずれにも平文で現れない
23. yt-dlp 更新ジョブが動作し、スモークテスト失敗時に直前バージョンへロールバックする
24. コンテナを削除・再作成しても、volume が残っていれば状態が完全に復元される
25. `make purge` が削除対象を事前表示し、実行後にホスト上へ残骸を残さない（`compose.privileged.yaml` を使用しない場合）
26. Task type `postprocess` と `worker-compute` が存在し、空チェーンを素通しする
